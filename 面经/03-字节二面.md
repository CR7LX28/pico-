### 1. 每个项目中，你学到最多的是什么？

> 以 Pico 为例，我学到最多的是怎么把多步 Agent 的失败变成可定位、可验证的问题。比如测试日志太长时，关键报错可能在末尾，单纯增加历史窗口会抬高每轮成本。于是我把长日志保存下来，只给模型预览和引用，再用定向测试验证它在新 run 里能否按引用找回旧 run 的报错。这样上下文治理可以用具体任务来验证。

其他项目用自己的经历填入四步叙述。说清当时遇到什么问题、你具体改了什么、用什么证据判断有效，以及这件事怎样改变了你后来的做法。 [长日志验证记录](../docs/architecture/context-history-upgrade-checklist.md)

### 2. 有哪些改进空间？和行业 SOTA 的差别是什么？

> 我会优先做模型感知的 token 预算，再补按需摘要。现在 Pico 用字符预算和确定性规则控制历史，优点是容易复现和排查，复杂任务里较早的设计决策却可能只剩很短的片段。我会先按目标模型的 tokenizer 计算输入预算、预留输出空间。只有旧历史靠规则处理仍装不下时，才生成带历史边界和来源引用的结构化摘要，同时保留近期原文。失败时退回已有摘要或规则裁剪。

行业对比可以选成熟产品公开的能力作参照，例如 Claude Code 的自动 compaction 和 Cursor 的按需上下文发现。回答差异时，分别比较预算计量、信息压缩和证据找回。要比较效果，就固定模型、仓库任务和工具权限，记录任务通过率、约束遗漏、重复读、输入 token 和耗时。Pico 仓库的离线数据可支持对应实验场景，尚无与这些产品同条件的排名。 [Pico 评测口径](../benchmarks/results/main-resume-repro-2026-06-07/DATA_PROVENANCE.md) · [Claude Code 上下文窗口](https://code.claude.com/docs/en/context-window) · [Cursor 动态上下文](https://cursor.com/blog/dynamic-context-discovery)

### 3. Pico 怎么把历史放进上下文？有何改进？Claude Code、Cursor 怎么做？

> Pico 的 session 按时间保存 user、assistant 和 tool 事件。调用模型时，`ContextManager` 把它们渲染成带角色的 transcript。工具事件会把工具名、参数和结果一起渲染，然后按预算选完整事件或短表示。旧的读文件证据失效时会提示重读。可以继续改进的地方是给旧历史建索引，模型发现缺细节时，按任务、文件名或错误码找回原记录。

Claude Code 公开文档描述了接近窗口上限时的自动压缩、手动 `/compact` 和部分内容的重新注入。Cursor 公开了把长工具输出变成可读文件，以及摘要后通过历史文件引用找回细节的做法。Pico 已把长 shell 日志做成可回读工件。当前普通历史主要在本轮组装时做规则压缩，按阈值做 LLM 摘要和通用历史检索是可以展开的设计。 [Pico 历史渲染](../pico/context_manager.py) · [Claude Code 压缩机制](https://code.claude.com/docs/en/context-window) · [Cursor 动态上下文](https://cursor.com/blog/dynamic-context-discovery)

### 4. 与 Claude Code 等相比有什么优缺点？为什么有上下文长度限制，过长会怎样？

> Pico 的优点是上下文从哪里来、按什么规则删、哪些证据过期，都能沿代码和 trace 解释，成本也容易做离线对照。缺点是字符预算对不同模型的 token 占用不够精确，规则短化可能压掉旧的语义关系。Claude Code 的自动摘要更适合把长任务持续推进，不过摘要也可能遗漏细节，关键约束仍适合保存在能持续加载的位置。

模型服务有支持的窗口上限，系统提示、工具说明、历史、当前输入和生成空间都要计入预算。典型稠密注意力的 prefill 计算量随序列长度近似二次增长，推理阶段的 KV cache 也会随上下文长度增长。输入变长会增加首 token 延迟、显存和费用。接近上限时可能挤掉输出空间，超限时可能被服务拒绝或截断，关键证据也可能淹没在低相关内容中。 [Transformer 原论文](https://arxiv.org/abs/1706.03762) · [Claude Code 上下文窗口](https://code.claude.com/docs/en/context-window)

### 5. 介绍一下 Transformer 架构。

> Transformer 先把 token 映射成向量并加入位置信息，再用堆叠的注意力和前馈网络更新表示。以自注意力为例，每个 token 生成 Q、K、V。Q 与 K 算匹配分数，缩放后做 softmax，用得到的权重对 V 加权。多头注意力并行学习不同关系。每个块还会做逐位置的前馈变换，并通过残差连接和归一化稳定深层训练。

原版是 **Encoder–Decoder**。Encoder 用自注意力编码输入，Decoder 用因果掩码防止看未来 token，再通过交叉注意力读取 Encoder 的表示。常见自回归 coding LLM 多用 **Decoder-only**，通过因果自注意力读取已有 token，输出下一个 token 的分布。注意力公式为 `softmax(QKᵀ / √d_k + mask) V`，缩放因子用来抑制维度增大时点积分数的幅度。 [Transformer 原论文](https://arxiv.org/abs/1706.03762)

### 6. 为什么自己写一个，直接用 GitHub 上的开源项目可以吗？

> 可以。这个项目当时的目标是把本地 coding agent 的关键行为拆开做实验。我需要控制每轮 Prompt、工具审批、checkpoint 和评测口径，才能单独改一种策略，再看同一组任务的结果变化。Pico 的流程是一个小的串行循环，所以自己实现核心控制逻辑，调试时可以沿一次模型调用定位到具体代码。模型后端和已有工具仍然可以复用。如果目标是尽快交付成熟的 IDE、插件或多用户能力，我会先评估现成框架的扩展点和维护成本。
