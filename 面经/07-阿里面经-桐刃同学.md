### 1. 结构化记忆怎么设计？长期记忆什么时候更新？Topic 怎么理解？

> 工作记忆主要给当前任务用，放最近文件、带版本的文件摘要和少量短期笔记。长期记忆存跨会话还会用到的事实。Pico 在 run 收尾时检查用户请求里是否有「记住」等沉淀意图，再从最终输出里抽取约定、决策、依赖或偏好格式的条目。临时任务状态、日志和疑似密钥会被筛掉。重复条目跳过，在同一分类下能识别到相同主语时，可以用新事实替换旧事实。

> Topic 是预设分类和存储入口，比如 `dependency-facts` 下可以存「Python 使用 3.12」，`project-conventions` 下可以存「集成测试用独立数据库」。`MEMORY.md` 做索引，`topics/<topic>.md` 保存具体条目。一个 Topic 可以存多条事实，运行时再按标签和关键词找与请求相关的条目。

当前意图和同主语替换靠规则匹配。如果后续要做多人共享，我会给记忆加来源、版本和作用范围，并对冲突事实做复核。 [长期记忆更新](../pico/runtime.py) · [Topic 存储与替换](../pico/features/memory.py)

### 2. 项目的意义和价值是什么？关键问题最后解决了吗？

> 我想验证本地 Coding Agent 能否在有限上下文里持续工作，尤其是反复读相同文件、日志太长和中断后丢任务进度这三个问题。Pico 分别用结构化记忆、长输出引用和 checkpoint 处理。能确认的是，在归档的脚本化记忆实验里，开启记忆后重复读由 60 次降到 0 次。定向恢复测试也验证了 Agent 可以从新 run 找回旧 run 的长日志报错。对更复杂的真实仓库和开放式任务，我会继续用真实模型、实际仓库任务和独立验收测泛化效果。

追问时交代对照条件。每个 variant 运行 60 次来自 12 个任务各 5 次。仓库另有上下文治理的字符数对照，字符降幅按字符口径讲。 [基准数据来源](../benchmarks/results/main-resume-repro-2026-06-07/DATA_PROVENANCE.md) · [上下文与恢复验证](../docs/architecture/context-history-upgrade-checklist.md)

### 2.1 你怎么约束模型？模型输出出问题怎么解决？

> 第一层用 Prompt 给出工具名、参数和输出协议示例。第二层由运行时解析动作，遇到空响应或坏 JSON 会发可修正的提示并限制重试。能解析的工具调用还要过参数、路径和审批校验，通过后才执行。第三层用真实测试或任务 verifier 判断结果。Pico 也会把没有工具标签的非空文本当作最终答案，这是当前解析兼容行为。即使它能正常收尾，仍要验证是否完成了用户要求。

具体例子可以用「模型返回一个不存在的工具」，解析出名称后由工具执行器拒绝，并把错误送回下一轮。若模型反复输出错误或后端调用失败，记录停止原因和 checkpoint，便于检查后重试。 [Prompt 协议](../pico/prompt_prefix.py) · [解析与重试提示](../pico/runtime.py) · [工具执行器](../pico/tool_executor.py)

### 3. 相关记忆什么时候召回？为什么没提供模型自主召回工具？

> 当前是每次组装 Prompt 时自动召回。它用本轮用户请求做查询，按标签命中、关键词重叠和时间排序，默认最多取 3 条，再受相关记忆分区预算限制。文件观察类笔记要匹配当前有效的文件摘要。这个方式在第一次模型调用前就能补足常见背景，也便于测试和解释召回结果。

> 如果任务中的检索意图在工具执行后发生变化，例如后续才发现一个新的错误码，我会考虑加只读 `search_memory`，让模型用新的关键词或文件名主动找。它要有作用域、Top-K、版本过滤和调用预算。自动召回保留作开场背景，自主召回用来补查缺失证据。可以用同一组多步任务比较召回质量、工具开销和验收通过率。

[自动召回与预算](../pico/context_manager.py) · [短期与长期记忆排序](../pico/features/memory.py)

### 4. 平时会用 Pico 跑复杂编码任务吗？一个任务大概多久？

> 我会按实际跑过的任务举例，比如【真实任务】，说清它涉及几个模块、用了哪个模型、做了哪些工具步骤、最后通过了什么验收。耗时以 run 的 wall-clock 为准。单次请求可以从 trace 的 `run_finished.run_duration_ms` 读到耗时。如果复杂任务跨多次 `ask()`，我会分别报各 run 累计时间和从任务开始到验收的总历时，是否含人工确认也要说清。

仓库有离线和脚本化验证，日常复杂任务的使用频率、真实任务耗时需用自己的记录补充。要报「一般多久」，用同类任务样本的中位数和样本量，样本多时再补 P95。模型调用、工具和人工审批的耗时可以分开说明。 [运行耗时字段](../pico/agent_loop.py)

### 5. 日均 token 消耗是多少？

> 我会先说明统计范围，比如只算 Pico 的最近 7 个自然日。对每次模型请求，把后端回报的输入和输出 token 分开记录，按日期求和后除以天数，并标注模型、每天任务量和 usage 覆盖率。若报的是活跃日均值，就单独注明分母。缓存命中量按后端口径单列，避免把已计入输入总量的缓存 token 再加一次。

Pico 的 trace 里，`model_parsed.completion_metadata` 可用于统计带 usage 的调用。单个 report 的提示词元数据对应最近一次调用，不能代表整个 run。缺 usage 或错误响应仍可能产生计费用量，完整账单应与后端用量记录对照。仓库里的 Prompt 字符数和离线 benchmark 无法给出个人日均 token，面试时按自己的日志或账单填。 [调用记录](../pico/agent_loop.py) · [后端用量解析](../pico/providers/clients.py)
