### 1. 如何评估 Agent 记忆召回的准确度？

> 我会拆成召回、注入、使用三段。先给每个查询标注应召回的记忆 ID、是否仍有效，以及哪些看似相关但应该排除。再用 Precision@K 看召回里有多少条真正相关，用 Recall@K 看应召回的证据覆盖了多少。Pico 默认最多选 3 条，既要看入选的候选，也要看预算裁剪后真正进入 Prompt 的条目。最后对照关闭记忆、注入无关记忆、正常召回和直接给正确记忆，测任务通过率、重复读和错误引用，区分是检索失败还是模型拿到证据后用错了。

测试集应包含无相关记忆、旧记忆过期、新旧冲突和同义改写。无相关记忆的样本单独统计误召回率，避免分母为零。Pico 归档的脚本化实验是 12 个任务、每组 60 次运行，关闭记忆时重复读 60 次，开启时为 0 次。它验证的是这批场景下的收益，归档的命中率口径也与 Precision@3、Recall@3 分开。 [Pico 召回实现](../pico/features/memory.py) · [评测数据口径](../benchmarks/results/main-resume-repro-2026-06-07/DATA_PROVENANCE.md)

### 2. 为什么要做 Pico 这个项目？

> 我想解决的是多步编码任务里容易重复找信息、上下文越来越长、出错后很难定位的问题。我希望自己能控制 Prompt 组装、工具权限和运行状态，知道一次失败来自模型选错动作、证据丢了，还是工具执行出了问题。因此做了一个小型本地 CLI，把每轮的状态和 trace 留下来，用固定任务对比开启和关闭某个机制时的差异。

具体可以接一个例子。长测试日志的预览和引用进入 Prompt，日志另存为本地工件，超过工件大小上限时会标记截断。这个设计可以用「恢复后还能不能沿引用找到日志尾部的关键报错」直接验证。 [架构总览](../docs/architecture/agent-harness-v1-overview.md) · [长日志验证记录](../docs/architecture/context-history-upgrade-checklist.md)

### 3. 如何判断模型调用 Skill 或 MCP 工具的意图是否正确？

> Skill 提供任务的操作流程和所需材料，MCP 工具提供可以实际执行的外部能力，两者可能在同一任务里一起用。我会先做一批带标签的真实请求，覆盖必须调用、可以用多种工具、应直接回答、需要先澄清或拒绝几类。评测时记录模型提议的动作，再分别判断 Skill 激活、工具选择、参数含义、权限时机和最终结果。比如调用到了查订单工具，但用错了订单 ID 或租户，选择和执行就要分开记分。

对必须调用的样本看漏调率，对无需调用的样本看误触发率，并单独统计高风险误调用。任务存在多条正确路径时，可以标注可接受的工具集合与必须满足的先后约束。用模拟服务执行，再用数据库状态或 verifier 检查结果。Pico 当前是内置工具注册表，这套评测是接入 Skill 或 MCP 时的设计。 [Agent Skills 规范](https://agentskills.io/specification) · [MCP 工具规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) · [Agent 评测方法](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

### 4. Agent 的数据隐私怎么保证？

> 我会先画清楚数据会经过哪里，包括模型、工具服务、记忆和日志。模型只收到完成任务必要的数据，敏感字段在出边界前过滤，保密仓库只接允许处理这类数据的推理服务。执行工具时，宿主按用户身份校验工作区、租户和目标资源，凭证只交给相应工具，高风险操作需要审批。工具返回、文件正文和网页都可能带有诱导指令，最终是否能读、写或发送由执行层决定。

Pico 已有工作区路径校验、高风险工具审批、shell 环境变量白名单，以及 trace、report 和长命令日志的脱敏。云模型仍会接收被送去推理的上下文，生产方案还要做工具进程和网络隔离、存储权限、留存策略及攻击回归测试。比如用带虚构密钥的文件模拟注入，分别检查模型请求、外部工具请求和落盘日志是否泄漏。 [Pico 工具执行](../pico/tool_executor.py) · [Pico 安全实现](../pico/security.py) · [OWASP Agent 安全指南](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html)

### 5. Agent 的稳定性怎么保证？

> 我会把可控的部分放到 Harness。动作过参数和权限校验，模型输出缺失或工具协议畸形时给明确错误并限制重试，命令有超时，重复调用有拦截。任务跑到边界就保存状态，让人能继续处理。完成与否尽量靠可执行验收。对网络类暂时故障可以做有限退避重试，涉及写入要先查真实结果，或者靠幂等键避免重复副作用。

Pico 当前有工具和重试步数限制、命令超时、重复调用拦截、checkpoint 和 trace。评测时对同一任务多次运行，分别统计任务通过率、格式错误、超时、人工接管、危险动作拦截和恢复结果。固定版本跑回归，改模型或 Prompt 后用相同任务集对比。 [运行循环](../pico/agent_loop.py) · [工具执行](../pico/tool_executor.py) · [Agent 评测方法](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

### 6. Agent 有 1%–5% 的不稳定性，怎么说服甲方采用方案？

> 我会先说明这 1%–5% 怎么测出来的，覆盖多少样本、哪些业务场景，失败是少给一条建议，还是会改错数据。可逆的低风险环节先做影子运行或人工确认的试点，和当前人工流程对比验收通过率、处理时长、接管比例和返工成本。高影响动作保留审批或规则校验，出现异常可以自动退回人工。试点前和甲方约定扩大范围的门槛、停用条件和责任人，到时候用数据决定是否推广。

如果样本少，就一起报告失败次数、总样本数和不确定性。试点可以先让 Agent 生成建议或草稿，由人工确认再生效，把「模型出错」和「错误实际影响业务」分开记录。

### 7. Agent Loop 是怎么实现的？

> 一次 `ask()` 创建 run 和 `TaskState`，先把请求写进 session，再组装 Prompt 调模型。解析结果分三条路。工具调用交给执行器校验和执行，结果写入历史、任务状态、trace 和 checkpoint，然后进入下一轮。工具格式错误会记录重试提示，受尝试预算限制。最终答案走收尾流程，保存状态和 report。模型接口失败也会写失败状态及 checkpoint，便于定位和续跑。

工具步数耗尽时还有一次仅收尾、不继续执行工具的模型请求。实际任务是否完成，可再用测试或 verifier 确认。 [Pico 入口](../pico/runtime.py) · [Pico Agent Loop](../pico/agent_loop.py)

### 8. 记忆系统是怎么设计的？

> 我把近期工作集和长期记忆分开。Session 内的工作记忆保存请求预览、最近文件、文件短摘要和少量过程笔记。读文件会生成短摘要，写入或检测到文件版本变化时会使旧摘要失效。长期记忆按项目约定、决策、依赖和用户偏好分类，以 Markdown 存到项目的 `.pico/memory/`。调用模型前按当前请求，从短期笔记和长期主题里找少量相关条目。

会话事件保存在 `history`，跨轮目标、有效约束、错误和验证证据保存在 `task_context`，各自按用途进入 Prompt。 [记忆实现](../pico/features/memory.py) · [任务状态](../pico/task_state.py)

### 9. Agent 上下文压缩是怎么实现的？

> Pico 在每次调用前把 Prompt 分为前缀、工作记忆和任务状态、相关记忆、历史、当前请求五段。历史按实际字符预算从新到旧选择，优先保留完整工具事件。放不下的旧记录换成短表示，重复读可以折叠，长 shell 日志用预览和工件引用。有效约束优先保留，当前请求完整放在末尾。裁剪会记录在 Prompt 元数据里，之后可以从 trace 看出哪些历史被缩短或省略。

当前默认总目标为 12,000 字符。LLM 摘要和基于模型 tokenizer 的预算是后续阶段。 [上下文实现](../pico/context_manager.py) · [升级清单](../docs/architecture/context-history-upgrade-checklist.md)

### 10. 说明上下文治理中各部分的预算比例及数据来源

> Pico 默认把完整 Prompt 的目标设为 12,000 字符。前缀、工作记忆、相关记忆、历史的初始预算分别是 3,600、1,600、1,200、5,200 字符。历史占比最大，因为工具调用和结果会持续累积。当前请求单独放在末尾，完整保留。它没有固定分区配额，但它和段间换行都计入整份 Prompt 的长度。预算按 Python 字符串长度计量，便于统一比较不同后端下的上下文治理效果。

| 分区 | 初始预算 | 占 12,000 字符的比例 | 内容 |
| --- | ---: | ---: | --- |
| `prefix` | 3,600 字符 | 30.0% | Agent 规则、工具定义与示例、工作区背景 |
| `memory` | 1,600 字符 | 13.3% | 优先放任务目标、有效约束和验证证据，再放请求预览、最近文件和文件摘要 |
| `relevant_memory` | 1,200 字符 | 10.0% | 按本轮请求召回的相关短期笔记和长期记忆 |
| `history` | 5,200 字符 | 43.3% | 用户消息、助手回复和工具事件，按预算保留原文或短表示 |
| `current_request` | 无固定配额 | 随输入变化 | 本轮用户请求原文 |

前四段预算合计 **11,600 字符**，与总目标相差 **400 字符**。400 是默认配置的差额。当前请求超过这段余量时，只要其他分区的实际内容较短，整份 Prompt 仍可能装得下。拼接后如果超预算，运行时会收缩可裁剪的分区。有任务状态时，普通历史会优先让出空间。保护内容过长时，运行时仍会完整保留当前请求，并通过 `prompt_over_budget` 标记结果。 [默认配置与裁剪逻辑](../pico/context_manager.py)

追问「数据从哪来」时，区分三件事。

- **默认配额**取自 `ContextManager` 的 `DEFAULT_TOTAL_BUDGET` 和 `DEFAULT_SECTION_BUDGETS`。表里的百分比是各段初始预算除以 12,000。
- **每轮实际占用**看 `trace.jsonl` 的 `prompt_built` 事件。各段的 `raw_chars`、`budget_chars`、`rendered_chars` 分别记录渲染前长度、当轮预算和最终渲染长度。结合 `budget_reductions` 和历史裁剪明细，可以查到哪些分区被缩减、哪些记录被省略。
- **比例怎么定的**可以解释各段的职责和取舍。仓库里的 12 组上下文压力实验对比了开启和关闭上下文治理时的 Prompt 字符数，并检查当前请求是否保留。若面试官问这组比例是否最优，可以如实说，现有实验回答的是裁剪效果，要比较配比还需要固定模型和任务，单独改变各段预算，观察任务通过率和关键信息保留率。
