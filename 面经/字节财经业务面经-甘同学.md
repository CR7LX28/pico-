## 1. 详细说明 Coding Agent 项目的模块、主循环流程以及如何串联各模块

> ✅ 短答：把 Pico 讲成一个本地 Coding Agent harness。模型负责决定下一步动作，harness 负责上下文、工具边界、状态记录、恢复和评测。

我会先解释为什么自己做这个项目。平时用 Claude Code、Codex、Cursor、Trae 这类工具时，很多关键环节对用户是黑盒，比如 prompt 怎么拼、上下文怎么放、工具在什么条件下会被调用、任务为什么停下、结果有没有被验证。Pico 的动机不是再做一个聊天助手，而是把这些环节拆出来，做成一个能观察、能恢复、能评测的本地 code agent。

从模块上看，Pico 可以拆成六层。第一层是入口和工作区层，负责解析当前目录、Git 状态、运行参数、provider、审批策略和项目文档。第二层是上下文层，ContextManager 会把项目规则、工作记忆、相关记忆、历史和当前请求装配成 prompt。第三层是模型层，模型只输出最终回答、重试信息或工具请求。第四层是 runtime 和工具层，runtime 解析模型输出，检查工具是否存在、参数是否合法、高风险动作是否要审批，再执行工具。第五层是状态和恢复层，TaskState、checkpoint、freshness 和 runtime identity 用来记录任务进度和恢复可信度。第六层是评测和工件层，trace、report、benchmark verifier 用来复盘过程和判断任务是否真的完成。

主循环可以按五步讲。第一步，系统装配运行现场，包括当前仓库、工具清单、项目文档、memory 和历史。第二步，构建本轮 prompt，把 stable prefix、memory、relevant memory、history 和 current request 分段放进去。第三步，请求模型，让模型返回工具调用或最终回答。第四步，如果是工具调用，runtime 先做白名单、参数、路径、重复调用和审批校验，再执行工具，把结果写回上下文。第五步，更新 task_state、trace、checkpoint 和 report。如果模型给出可解析 final answer，或者触发 step limit、retry limit 这类停止边界，循环结束。

## 2. 举例说明 Coding Agent 的实际应用场景，如输入内容及对应操作

> ✅ 短答：典型场景是仓库级任务，比如"这个测试失败了，帮我定位并修复"。Pico 会先读项目规则和相关文件，再搜索定位问题，用受控工具修改，最后跑验证并留下运行工件。

可以举一个最容易讲清楚的场景：用户在仓库里输入"这个单测挂了，帮我定位原因并修一下"。Pico 不会直接让模型凭经验猜答案，而是先加载工作区上下文：当前目录、项目文档、工具说明、最近历史、已有记忆和用户请求。随后模型可能先调用搜索工具定位失败测试名或错误关键词，再读相关文件。如果发现问题出在某个函数的边界处理，它会通过 patch 工具做精确修改，然后运行相关测试或命令验证。

整个过程里，每一步都有边界。读文件、搜索是低风险工具；跑 shell、写文件、patch 文件是高风险工具，需要受审批策略控制。patch 也不是让模型随便重写文件，而是要求旧文本精确命中一次，避免模糊替换。工具失败也不会直接让任务结束，比如路径错了或命令失败，失败结果会进入下一轮上下文，让模型修正方向。

## 3. 解释 Coding Agent 中审批策略的触发条件

> ✅ 短答：审批只针对高风险工具触发。读、列、搜这类低风险动作按参数校验执行；run_shell、write_file、patch_file 这类会执行命令或修改工作区的动作，会进入审批策略。

Pico 的审批策略不是所有工具每次都问用户，也不是模型自己决定要不要审批。工具在注册时就有风险属性。低风险工具主要是 list_files、read_file、search 这类读操作，它们不会修改工作区；高风险工具包括 run_shell、write_file、patch_file，因为它们可能执行命令、写文件或修改代码。

执行链路是 fail-closed 的。runtime 会先判断工具名是否在白名单里，再检查参数是否合法，比如路径不能逃出工作区、搜索模式不能为空、shell timeout 不能越界、patch 的 old_text 必须精确命中一次。然后再判断是否触发重复调用保护。只有这些基础校验都过了，高风险工具才进入 approval policy。

这里可以引用工具设计题里的说法：工具更多不等于系统更强，关键是工具有没有清晰目的、schema、风险等级和统一执行闸口。Pico 的工具层本质上是显式工具表加统一 runtime 网关，不是让模型裸奔调用外部动作。

## 4. 说明审批策略的设置位置及是否每次对话都需指定

> ✅ 短答：审批策略是这次运行的 runtime policy，启动时指定，不是每一轮对话都重新指定。CLI 参数是 `--approval ask|auto|never`，默认是 `ask`。

审批策略是在启动 Pico 时设置的，属于这次 run 的运行身份之一。它会进入 runtime identity，恢复时也要检查。因为同一份 checkpoint 如果上次在只读或 ask 模式下生成，这次换成 auto 或可写模式继续跑，风险边界已经不同，不能假装还是同一个运行现场。

三个策略的含义要讲准确。`ask` 表示高风险工具需要用户确认；`auto` 表示高风险工具自动放行；`never` 表示高风险工具一律拒绝。低风险的读、列、搜仍然可以在参数校验后执行。所以 `never` 不是"整个 agent 不能用工具"，而是不能执行会带副作用的工具。

如果面试官追问"为什么不每轮都指定"，可以说审批策略不是业务参数，而是运行时安全策略。每轮重复指定会增加交互成本，也容易造成状态不一致。更合理的做法是把它作为 run 级别配置，写进 runtime identity 和 trace，这样恢复、审计、评测时都能知道当时是在什么权限边界下执行的。

## 5. 阐述审批超时情况下 Agent 的处理方式

> 💡 短答：Pico main 没有实现审批超时队列。当前审批是同步输入，读不到确认就等价于拒绝，不会后台自动放行。shell timeout 是命令执行超时，不是审批超时。

Pico main 里审批不是一个异步队列，也没有"用户一段时间不处理就自动继续"的机制。高风险工具需要确认时，runtime 会同步等待输入；如果没有拿到明确同意，应该按拒绝处理。这样做的好处是默认安全，不会因为用户没响应就让 agent 执行有副作用的动作。

要区分两种 timeout。审批超时是人机交互层的问题，Pico main 目前没有做成独立超时状态机；shell timeout 是工具执行层的问题，用来限制命令最多跑多久，防止命令卡死。两者不要混讲。

如果继续做产品化，可以把审批做成一个可恢复的 Pending Action，而不是同步阻塞输入。高风险工具调用会生成一条 ApprovalRequest，记录工具名、参数摘要、风险等级、workspace fingerprint、runtime identity 和过期时间。超时后默认 fail closed，不会自动执行原动作；runtime 会把审批过期作为结构化结果回灌给 agent，让它只能选择只读调查、生成 diff、输出计划或安全结束。对可逆写操作，可以先生成 staged diff，等用户回来后再批准应用；对 shell、删除、网络访问这类高风险动作，超时后一律 expire。这样既保留了 agent 的推理成果，又不会因为用户离开而扩大权限边界。

> 注：codex 最近上新了新的权限审批超时方式，超过一分钟会自动帮用户选择它推荐的方式（20260701）

## 6. 询问是否用到 subagent 相关能力及具体实现

> ✅ 短答：Pico main 有 `delegate`，但它不是并行可写 worker 池，而是受限、只读、带深度和步数上限的调查子 agent。

Pico main 里确实有 subagent 形态的能力，叫 `delegate`。它的定位是把一个小调查任务交给子 agent，比如"帮我只读看一下这个模块的职责"或"调查这个错误可能来自哪些文件"。子 agent 返回的是 `delegate_result`，父 agent 再决定下一步。

> v3 版本支持了 subagent，后续会把相应的设计文档补上。

## 8. 询问 AGENTS.md 中包含的内容

> ✅ 短答：Pico 会把 `AGENTS.md`、README、项目配置等作为工作区前缀的一部分，让模型先看到项目规则和基本信息。它更像轻量项目导航包，不是复杂的多层规则继承系统。

可以这样回答：`AGENTS.md` 一般放的是项目级指导，比如项目结构、编码规范、测试命令、禁止事项、常见工作流和仓库里的特殊约定。对 coding agent 来说，这类文件相当于稳定上下文的一部分，让模型在开始任务前知道这个仓库怎么工作。

Pico main 的实现比较轻量。workspace 会扫描 `AGENTS.md`、`README.md`、`pyproject.toml`、`package.json` 这类文件，并把它们裁剪后放到 prefix 里。prefix 的价值是稳定、可复用、对工具调用格式和项目基线有影响，所以它在预算裁剪里优先级比较高，最后才动。

不要把它说成 Claude Code 那种完整规则体系。Pico main 里没有多层 `AGENTS.md` 继承、冲突解析或自动 memory promotion 的复杂系统。面试时可以说：当前版本先做轻量项目导航，后续如果扩展，会考虑更清晰的规则层级、作用域和冲突处理。

## 9. 举例说明通过优化提升 Coding Agent 结果准确性的方法

> ✅ 短答：准确性不是单点 prompt 优化，而是输入准确、执行准确、状态准确、验证准确一起做。Pico 的例子可以讲上下文分层、工具校验、重复读取治理、大文件策略、恢复校验和 benchmark。

我会先把"准确性"拆开。第一层是输入准确：模型看到的是当前任务需要的信息，而不是一大坨历史。Pico 通过 ContextManager 把 prefix、memory、relevant memory、history、current request 分层，超预算时按顺序裁剪，当前请求尽量不裁。第二层是执行准确：所有工具调用都要经过 parse、参数校验、路径边界、重复调用拦截和审批。第三层是状态准确：file summary 有 freshness，checkpoint 有 runtime identity，恢复时不会盲信旧状态。第四层是验证准确：任务完成不靠模型自己说，而是看 verifier、测试、产物和运行工件。

可以举"重复读取治理"的例子。不是同一个文件读第二次就叫错。执行层只拦明显坏循环：同一工具、同一参数、连续发生且没有新增信息。比如最近两次工具事件已经同名同参时，再次同名同参会被拒绝。但同一个文件分段读取、patch 后复查、带着更具体问题回看局部，都不应该被误杀。语义层的重复主要通过上下文整理处理，把旧 read 结果折叠掉，复用 file summary，让 prompt 里少堆重复信息。

还可以举"大文件"的例子。遇到一万行 Java 或 C++ 文件，不应该把整文件塞给模型。正确流程是先定位，再钻取，再验证：先看报错栈、测试失败、最近改动和搜索命中，把范围缩到几个方法或代码块；再局部读取；读完形成带 freshness 的摘要；最后做小范围 patch 并跑最小验证集。Pico main 目前有按路径读、搜索和局部读取，LSP、ctags、tree-sitter、调用图、按符号 patch 属于未来工具增强，不能说成现状。

如果面试官追问"怎么减少幻觉"，可以说：我不是只靠提示词让模型别瞎编，而是让它通过工具拿证据，让 runtime 拦危险动作，让 memory 只当索引，让恢复机制检查旧状态，让 benchmark 检验结果。这样错误会更早暴露在工具、状态或 verifier 层，而不是最后靠人读 final answer 猜。

## 10. 说明上下文治理中各部分的预算比例及数据来源

> ✅ 短答：Pico main 默认总预算是 12000 字符，prefix 3600，memory 1600，relevant memory 1200，history 5200，current request 不放进固定预算里，原则上完整保留。数据来源是 `ContextManager` 默认配置和 prompt metadata。

这里要先强调，Pico 现在用的是字符预算，不是 tokenizer 级精确 token 预算。原因是不同 provider 的 tokenizer 不一样，同一段中文、代码和日志在不同模型里切出来的 token 数可能不同。Pico 这个阶段更想验证上下文治理机制本身，所以先用字符数作为跨 provider 的统一近似指标。

| section | 默认预算 | 作用 |
|-|-|-|
| `prefix` | 3600 字符 | 稳定上下文，包括 agent 规则、工具协议、工具清单、项目导航。 |
| `memory` | 1600 字符 | 当前任务仪表盘，比如 task summary、recent files、file summaries、episodic notes。 |
| `relevant_memory` | 1200 字符 | 按当前请求召回的少量相关旧事实。 |
| `history` | 5200 字符 | 最近对话、工具调用和工具结果，旧输出可以折叠。 |
| `current_request` | 不计入固定 section 预算 | 当前用户真正要解决的问题，尽量完整保留并放在最后。 |

如果面试官问比例怎么来的，可以说这不是拍脑袋写在文档里，而是代码里的默认配置，并且每轮 prompt 构建时会把 raw chars、budget chars、rendered chars、是否发生裁剪等信息记录进 prompt metadata。这样压缩不是黑盒，后续可以复盘这一轮到底是谁被裁了、为什么被裁。

## 11. 询问上下文裁剪的顺序

> ✅ 短答：超预算时先压 `relevant_memory`，再压 `history`，再压 `memory`，最后才动 `prefix`。`current_request` 不裁剪。

这个顺序背后的逻辑是不同信息寿命不同。相关记忆可以重新召回，旧历史可以折叠，工作记忆可以压缩，但 prefix 里有工具协议、项目规则和基本边界，过早裁掉会影响工具调用稳定性。current request 是这一轮真正要对齐的目标，如果它被历史淹没或裁掉，agent 最容易跑偏。

上下文膨胀不是 token 问题，而是状态管理问题。不能把所有东西都总结成一段，也不能粗暴从尾部截断。Pico 的做法是每一轮重新装配 prompt，把不同寿命的信息分到不同 section，再按优先级收缩。

如果追问"只做 summary 行不行"，可以说 summary 能降成本，但会有摘要漂移，一旦摘要写偏，后面会一直基于错误状态继续。只做滑动窗口最便宜，但会丢早期约束。只做检索适合静态知识，不适合动态任务状态。Pico 选择的是结构化状态、短摘要和本地工件结合：高价值状态进 task_state 和 memory，完整过程留 trace/report，当前 prompt 只带本轮需要的高价值信息。

## 12. 解释相关记忆的检索策略

> ✅ 短答：Pico main 的相关记忆召回是可解释规则，不是向量数据库。它主要看 tag 精确命中、关键词重叠、时间新旧和插入顺序，最多取少量候选。

相关记忆的目标不是让模型背下所有历史，而是减少重复探索，并提醒模型哪些旧事实可能和当前任务相关。main 分支的召回更偏透明规则：先看 query 和 note 的 tag 是否命中，再看关键词重叠，再考虑时间和 note_index，默认只取少量候选，避免 relevant memory 自己变成新噪声。

召回结果最好带来源。比如这条记忆来自哪个文件摘要、哪次运行、哪条测试结果或哪个任务阶段。如果没有来源，就只能当提示，不能当事实源。Pico main 现在最重要的是 file summary 有 freshness，恢复时 stale paths 会显式带回上下文，关键动作前仍要回读当前文件和工具结果。

## 13. 说明 tag 的定义方式及如何弥补其对准确性的影响

> ✅ 短答：tag 是轻量标签，通常来自路径、主题、来源或偏好类型。它的好处是透明、可调试，缺点是同义表达覆盖弱，所以要用关键词、freshness 和回读证据来弥补。

tag 不要讲成复杂 ontology。Pico 里更适合把它理解成一个轻量索引，比如某条 note 和哪个路径、哪个主题、哪类用户偏好、哪类项目事实有关。这样召回时能用明确规则判断"为什么这条记忆被带进来"。

tag 的问题也很明显：它对同义表达不敏感。用户问"测试命令"，而记忆 tag 写的是"verification"；用户问"权限模块"，而旧 note 用的是"authz"，就可能召回不到。弥补方式不是把 tag 设计得很重，而是几层信号一起用：tag 精确命中、关键词重叠、路径或模块名、时间新旧、freshness 是否有效。

最终还要回到代码事实。tag 只能告诉模型"可能该看这里"，不能代替当前文件内容。面试里可以说：我会把 tag 当成导航线索，而不是事实裁决。真正要改代码前，还是要读当前文件、看当前测试和当前工具结果。

## 14. 阐述不同层记忆出现冲突时的解决办法

> ✅ 短答：当前工作区真实文件和工具结果优先，其次是 freshness 有效的 file summary 或 checkpoint，再往后才是 working memory 和 durable memory。memory 是索引，不是事实源。

可以先说冲突来源。长任务里可能出现三类冲突：文件已经变了，但旧摘要还在；当前任务状态和 durable memory 的历史经验不一致；用户当前请求和早期历史目标不一致。解决这类问题不能靠模型自己判断哪条更像真，而要有证据优先级。

Pico 的原则是当前事实优先。当前文件内容、当前命令输出、当前测试结果，是最强证据。freshness 有效的 file summary 或 checkpoint 可以参考；如果 freshness 失效，旧摘要要降权或失效。working memory 记录当前任务进度，durable memory 只放长期稳定事实，不应该把 transient task state 写进去。

Pico 会用 freshness 失效旧 file summaries 和 checkpoint key files，并把 stale paths 带入恢复上下文；真正下结论或修改前，回答策略上应回读当前文件和工具结果。这个回读是操作纪律，不是所有写操作的 runtime 强制 gate。比如 patch_file 会要求 old_text 精确命中一次，但 write_file 并不天然强制你先读。

## 15. 解释关键文件的 freshness 和 runtime identity 校验恢复状态的作用

> ✅ 短答：freshness 判断关键文件有没有变，runtime identity 判断运行现场是不是同一个。它们共同决定旧 checkpoint 还能信多少。

恢复机制要解决两个问题：从哪里接着做，以及旧状态现在还可信吗。freshness 解决的是文件可信度。Pico 会记录关键文件当时的内容指纹，如果恢复时文件 hash 变了，说明旧的文件摘要、旧结论、旧下一步可能已经不可靠。这种情况不是一定完全不能恢复，而是要标成 partial stale：任务目标和大方向可以参考，但涉及变更文件的判断必须重新读取。

runtime identity 解决的是运行现场可信度。它会记录 cwd、模型、model client、approval policy、read only、max steps、max new tokens、feature flags、shell 环境白名单、workspace fingerprint、tool signature 等。如果这些变化了，旧 checkpoint 的风险边界也变了。比如上次是只读模式，这次是可写模式；上次工具签名是一套，这次工具变了；上次在一个工作区，这次换了仓库。此时不能把旧状态当成同一个现场继续跑。

面试里可以用一句话总结：freshness 防止 agent 误信旧文件，runtime identity 防止 agent 误信旧运行环境。对 code agent 来说，忘记旧状态最多多读一遍；误信旧状态会把后续执行全带偏。

## 16. 说明状态恢复时重新锚定的方式

> ✅ 短答：恢复不是把聊天记录重放给模型，而是把经过校验的任务状态重新装配成一张任务仪表盘。模型接手时能看到目标、卡点、下一步、关键文件、哪些路径 stale、当前恢复状态是什么。

重新锚定可以按三步讲。第一步是加载旧 checkpoint 和会话状态，拿到当前目标、已完成内容、卡点、下一步、关键文件和当时的运行身份。第二步是校验 freshness 和 runtime identity，判断 full valid、partial stale、workspace mismatch、schema mismatch 或 no checkpoint。第三步是把结果显式放进下一轮 prompt，让模型知道哪些旧信息可信，哪些必须重新确认。

如果关键文件 stale，下一步不是继续基于旧摘要写代码，而是先读当前文件。系统不会假装旧状态一定正确，也不会自动做全仓依赖分析。它做的是把恢复风险显式化，让模型在当前工作区事实上重新对齐任务。

这里可以补四篇面经里的表述：Pico 恢复的是经过校验的任务状态，不是聊天记录。完整历史可以留在 trace 和 report 里用于复盘，但不应该原样塞回 prompt。prompt 里要放的是当前推理需要的高价值信息。

## 17. 详细讲述 Coding Agent 评测的校验逻辑

> ✅ 短答：Pico 的评测不是看 final answer 像不像对，而是把任务写成可检查的契约：prompt、fixture repo、allowed tools、step budget、expected artifact、verifier、category 和停止条件。

我会先说明为什么 coding agent 评测和普通问答不一样。普通问答更多看回答是否覆盖要点；code agent 要看它有没有把仓库改成预期状态、有没有遵守工具边界、有没有在预算内完成、有没有留下可复盘证据。模型说"我完成了"不等于真的完成。

Pico 的 benchmark 任务会先定义固定格式：任务 id、用户 prompt、fixture repo、允许用哪些工具、最多多少步、预期产物是什么、用哪个 verifier 检查、属于哪类任务。执行时复制干净 fixture，用 deterministic scripted model 跑固定任务，再检查产物、预算、停止原因和 verifier 结果。这样评的是 harness 和 runtime 合同，不是某个真实 provider 的上限。

过程证据分三层。第一层是 `task_state.json`，看状态、步数、last tool、stop reason 和 final response。第二层是 `trace.jsonl`，看 `run_started`、`prompt_built`、`model_requested`、`model_parsed`、`tool_executed`、`checkpoint_created`、`run_finished` 等事件。第三层是 `report.json`，汇总 task_state、prompt metadata、durable memory promotions 或 rejections 和脱敏环境信息。它不是完整 prompt、raw model response 或 memory diff 回放。

## 18. 询问如何通过校验判断半开放性问题的结果是否符合预期

> ✅ 短答：半开放问题不能只看最终回答语气，要先把"什么算答对"写成 checklist。可自动化的用 verifier，不能完全自动化的用 trace/report 加人工审阅。

半开放问题的难点是没有唯一字符串答案，但仍然可以有验收标准。我会先把题目约束、必要证据、允许动作、风险说明和禁止越界写成 checklist。比如"请分析这个模块并给改造建议"，可以检查它是否读了当前文件、是否覆盖关键约束、是否引用了真实代码证据、是否说明了没有验证的部分、是否没有擅自修改文件。

能自动化的部分尽量自动化。比如目标文件是否存在、patch 是否命中、测试是否通过、输出 JSON 是否符合 schema、是否超出工具预算、是否调用了禁止工具，这些都可以写 verifier。不能完全自动化的部分，用 trace/report 支撑人工审阅。审阅时看 agent 到底读了什么、跑了什么、哪里失败过、最后为什么停，而不是只看 final answer 写得像不像。

如果把 PRD 自动实现当成半开放任务，验收清单会更明显：需求是否被拆成目标和非目标，计划是否列出修改范围，执行是否只通过受控工具，验证是否覆盖格式、类型、单测和需求 checklist，收尾报告是否列出实现内容、修改位置、测试结果、未跑测试原因和剩余风险。这样人不需要从头盯每一步，但最后能基于证据判断这次变更是否可信。

这题的核心是把"开放"变成"可审阅"。不是所有判断都能完全自动化，但每个判断都应该有证据入口。对 Pico 来说，这个证据入口就是 task_state、trace、report、verifier 和必要的人工 review。
