### 2. 了解哪些 Agent 范式？

> 我会先区分预设工作流和由模型决策的 Agent。流程已知时，可以用串联、路由或并行。下一步依赖现场结果时，可以用 ReAct，让模型根据当前信息选择动作，工具给回观察结果，再决定下一步。复杂任务可以先规划再执行，发现证据与计划冲突时重规划。能明确验收的任务也适合生成、验证、修订的循环。Pico 最接近受约束的 ReAct 式循环，每步由模型选择一个工具或给出最终答案，Harness 管工具执行和停机。

例如定位未知测试错误适合边查边走。固定格式检查、类型检查和测试可以由确定性程序执行，并把结果交回 Agent。 [ReAct 论文](https://arxiv.org/abs/2210.03629) · [Anthropic Agent 工作流](https://www.anthropic.com/research/building-effective-agents) · [Pico 主循环](../pico/agent_loop.py)

### 3. 介绍 Agent 项目

> Pico 是一个在本地代码仓库里工作的 Python CLI，可以通过模型查代码、改文件和跑测试。一次请求进来后，程序先整理仓库信息和会话状态，再让模型提出一个动作。执行前做参数、路径和权限检查，执行后把结果写回下一轮上下文，同时保存 checkpoint 和 trace。我重点解决的是长任务容易丢信息的问题。现在会按预算选历史，把有效约束放进任务状态，长命令日志只把预览和引用给模型，续跑时可以回读旧 run 的日志。离线评测用固定任务和验证器来检查这些机制。

可追问的一个案例是定向测试里，Agent 在恢复后的新 run 中按引用找回了第 1,205 行的错误。该用例使用脚本化模型，验证的是运行机制。 [Pico 架构](../docs/architecture/agent-harness-v1-overview.md) · [验证记录](../docs/architecture/context-history-upgrade-checklist.md)

### 4. 整个代码仓库很大，模型上下文会无限增长，怎么解决？

> 我会分开处理仓库发现和上下文注入。先给目录、关键约定和入口，模型根据报错、文件路径或符号用搜索定位，再按行读相关实现和测试。对反复定位的大仓库，可以加按提交或文件哈希增量更新的符号索引，再按相关性取少量片段。工具结果进入 Prompt 前还要过预算，长日志用引用，需要时按范围读回。

Pico 已有 Git 与少量白名单文档片段组成的工作区背景，以及 `list_files`、`search` 和 `read_file`。增量符号索引是扩展设计。整仓发现、历史长度和单次输出大小分别设预算，可以把爆量的来源定位到具体阶段。 [工作区快照](../pico/workspace.py) · [工具实现](../pico/tools.py)

### 5. 长链路和长对话让模型注意力分散，怎么靠 Agent 解决？

> 我会让每一轮围绕当前子任务组上下文。目标、有效约束、当前阻塞和最近验证结果从任务状态重新注入，近期动作留足细节，旧过程按需检索。调查多个独立问题时，可以让只读子 Agent 各自看相关文件，主 Agent 只收结论和证据位置。每过一个阶段，先用测试或其他可核对的结果确认，再更新 checkpoint。比如用户早期要求保持公共 API，后面跑了很多轮命令，这条要求也会作为有效约束出现。

长窗口里的信息利用率会受证据位置影响。Pico 当前已实现动态历史窗口和有效约束保留，通用旧历史检索仍可继续做。 [长上下文研究](https://arxiv.org/abs/2307.03172) · [任务状态](../pico/task_state.py) · [上下文组装](../pico/context_manager.py)

### 6. 项目规模多大？代码量是多少？

> 按当前工作区统计，`pico/` 下有 24 个 Python 文件、约 7,200 行，`tests/` 下有 19 个 Python 文件、约 3,850 行。主包和测试合计约 1.1 万行。主包主要分成 CLI 和运行循环、工具和安全、上下文和记忆、状态与持久化、模型适配和评测。

精确统计为主包 **7,209 行**，测试 **3,846 行**，合计 **11,055 行**。统计的是这两个目录里 `.py` 文件的物理行数，包含注释和空行，也包含当前工作区新增的测试。文档、依赖、脚本和 Mini Pico 示例另计。

### 7. 用户要恢复到对话的某个节点，要怎么做？

> 我会先确认是回到那条对话继续、回滚代码，还是两者都要。Claude Code 可以用 `/rewind` 选择对应的用户消息，并选择恢复对话、代码或两者。做自己的实现，我会给事件加稳定 ID 和父节点引用，在可恢复的消息边界保存任务快照及工作区基线。选中节点后，从那个位置创建新会话分支，重放至多到该节点的会话状态。代码如需恢复，可从对应提交和补丁在隔离工作区重建。

Pico 当前 CLI 的 `--resume` 按会话 ID 加载最近保存的会话状态，任意对话节点分叉是扩展方案。需要显式区分对话分支与工作区快照。数据库写入、远端请求等外部副作用要检查真实状态，按业务能力做幂等或补偿。 [Claude Code Checkpointing](https://code.claude.com/docs/en/checkpointing) · [Claude Code 会话分支](https://code.claude.com/docs/en/sessions#branch-a-session) · [Pico CLI](../pico/cli.py)

### 8. 了解 CC 和 Hermes 后，如果你是 CC 开发者，会迭代什么模块？

> 我会优先做一个跨会话的任务交接模块。借鉴 Hermes 把可复用经验沉淀成记忆或 Skill 的思路，把当前任务的目标、验收条件、关键决策、未解决错误和证据引用保存成可编辑的交接记录。下一次进入仓库，先按任务和文件匹配候选记录，再检查提交和文件指纹，过期证据提示重查。复用多次且验证有效的操作步骤，再建议沉淀成团队 Skill。

CC 已有自动记忆和会话管理。这个迭代聚焦于任务级证据、版本新鲜度和交接过程是否可追溯。效果可以用接手成功率、重复读次数和错误记忆命中率衡量。 [Claude Code 记忆](https://code.claude.com/docs/en/memory) · [Hermes Agent 文档](https://hermes-agent.nousresearch.com/docs)

### 9. 单 Agent 难以高效处理大项目，多 Agent 又增加编排难度，怎么做？

> 我会先按任务依赖拆分，能并行且边界清晰的部分才交给多个 Agent。比如查三个模块的调用方可以并行做只读调查。需要共同修改同一公共接口时，由一个 Agent 定契约，再把各模块的适配分给不同 worker。每个 worker 只拿自己的目标、可改范围和验收条件，输出 diff、证据和测试结果。主 Agent 控制依赖、预算和合并顺序，统一跑集成测试。

写入任务可用独立 Git worktree 隔离，避免互相覆盖。用同一批任务比较单 Agent 和并行方案的总耗时、总 token、冲突次数和验收通过率。Pico 的 `delegate` 是受限的只读调查，写入编排与合并是扩展设计。 [Orchestrator–workers 模式](https://www.anthropic.com/research/building-effective-agents) · [Pico 子 Agent](../pico/runtime.py)

### 10. 了解 Ruflo 吗？它怎么解决多 Agent 编排问题？

> 从项目公开资料看，Ruflo 给 Claude Code 等客户端提供多 Agent 编排能力，可以通过 MCP 接入。它把任务协调、Agent 分工和共享记忆放到统一的工具层，给主 Agent 提供分发任务和查看进度的入口。这个方向解决的是多 Agent 的协调成本。实际项目里我仍会确认任务边界、写入隔离、失败重试和最终验收由谁负责，再决定要接入多少能力。

面试中可如实区分读过文档、看过源码和实际跑过。若被问值不值得用，可以拿同一组独立任务比较串行执行、简单的主从分工和 Ruflo 编排。 [Ruflo 官方仓库](https://github.com/ruvnet/ruflo)

### 11. 了解软件工程 3.0 的开发范式吗？

> 如果这里说的是 AI 参与软件全生命周期，我理解有两个典型变化。小原型可以用自然语言快速试错。需要协作和长期维护的功能，更适合规范驱动开发，也就是先写清需求、接口、边界和验收标准，再由 Agent 生成计划、拆任务和实现，通过测试与评审验证。人的工作会更多放在确定目标、约束和验收，以及处理架构和上线决策。

可以举后台接口的例子。先定请求和返回、幂等键、并发重复提交的语义，再把这些条件变成验收测试，最后让 Agent 分步实现。这是一种具体开发实践，可按面试官使用的「3.0」口径继续讨论。 [腾讯云技术沙龙分享](https://developer.cloud.tencent.com/article/2646440) · [GitHub Spec Kit](https://github.github.io/spec-kit/quickstart.html)

### 12. 如果 token 不限、可以用最强模型，会把更多成本花在哪个环节？

> 我会把主要预算花在高风险决策和独立验证。比如做订单状态迁移，我会先让强模型读现有调用链、事务和重试逻辑，列出可能的竞态和兼容方案。实现以后，再让独立视角围绕异常、并发和回滚设计反例，用真实测试和数据核对。例行改动用已有工具执行，人的时间留给业务取舍和发布风险。

可接一句“即使 token 不限，团队注意力和验证时间仍有限”。给出一个想多花成本查清的具体风险，比罗列模型名称更能说明取舍。

### 13. 模型或 Agent 对需求理解不到位，怎么解决？

> 我会先让它复述需求，列出目标、约束、假设和验收标准，再拿几个正反例核对。会影响接口或数据一致性的歧义，先问业务方。能通过仓库和日志查清的，给它准确的入口和证据。确认后把决定写进任务说明和验收测试，让后续每个阶段都能重新对照。实现后的复核直接从需求出发，逐条对照行为和结果。

例如「重复下单」可能指客户端超时重试，也可能指用户主动买两次。先定幂等键的来源、范围和有效期，再写并发重试用例。 [Spec Kit 规范驱动开发](https://github.github.io/spec-kit/how-to/sdd.html)

### 14. AI 写的代码看起来没问题、测试也过了，但可能还有小问题，上线前怎么查？

> 我会先按本次 diff 找受影响的接口、数据库和依赖，检查现有测试覆盖的是不是生产中的真实失败方式。比如库存扣减，要专门测重复请求、并发更新、事务部分失败和下游超时。随后用接近生产的配置做集成或预发验证，确认迁移顺序、兼容性和回滚路径。上线前把灰度范围、监控指标和停止条件定好，比如错误率、P95 延迟和业务对账差异，才能在小范围异常时及时回退。

追问「测试绿了为什么还有问题」时，可以说测试依赖样本、环境和断言。重点核对模拟服务是否掩盖了真实行为，以及断言是否覆盖业务不变量。

### 15. AI Coding 时多轮交互效果反而更差，还浪费成本，平时怎么做？

> 小而明确的需求，我会在第一条里给目标、边界、相关文件、例子和验收命令，让 Agent 做到可验证结果。复杂需求分成对齐方案、实现和验证几个阶段，反馈集中到明确的里程碑，避免每一小步重复发同一份背景。如果对话里已经混进大量失败尝试，我会用一份简洁的交接记录开新上下文，带上当前 diff、已验证事实和未解决问题。

衡量时看完成同一个验收目标的总耗时、token 和返工次数。多轮有价值的地方是逐步获得新证据，例如工具真实报错或用户确认了歧义。 [Claude Code 最佳实践](https://code.claude.com/docs/en/best-practices)

### 16. 无限循环、无意义的循环怎么处理？

> 我会用预算和进展检测两层约束。先对工具步数、重试次数、耗时设硬上限，外部命令也有超时。再监控每轮是否产生新证据，例如测试失败是否减少、错误是否变化、文件状态有没有改变。同一命令、同一错误、同一工作区连续出现时，要求更换假设或退出。退出时保存已尝试内容、阻塞和下一步，便于接手。

Pico 已限制工具步数和格式重试，并拦截重复的相同工具调用。进一步可以用归一化动作、错误签名和工作区指纹识别 A→B→A 的循环。对可能产生副作用的调用，重试前先检查是否已生效。 [Pico 主循环](../pico/agent_loop.py) · [重复调用拦截](../pico/tool_executor.py)

### 17. 知道 Claude Code 的 `/goal` 吗？能解决上面的问题吗？

> `/goal` 可以给当前会话设置完成条件。每轮结束时，一个独立的评估模型根据对话里呈现的证据判断目标是否满足，没满足就让 Agent 继续。它能减少每次都要手动说「继续」，也能缓解 Agent 提前停下。要避免无意义循环，我会把条件写成可观察的结果，再加时间或轮次上限。评估模型依据对话中的证据作判断，真正的通过结果来自测试或检查命令。

例如 `/goal 修复订单重试导致的重复扣减，提供回归测试退出码和并发用例结果，保留已有断言，最多执行 8 轮`。对强制验收可以另加可执行检查和硬性预算。 [Claude Code /goal](https://code.claude.com/docs/en/goal) · [Claude Code Hooks](https://code.claude.com/docs/en/hooks)

### 18. OpenClaw 和 Claude Code 各有何优缺点？使用体验如何？

> 我会按工作场景比较。OpenClaw 更像接在聊天渠道上的通用 Agent，可以用 Gateway 把消息、工具和定时任务接起来，适合跨渠道提醒和日常自动化。代价是要自己维护渠道、权限、部署和插件配置。Claude Code 的入口更贴近仓库开发，读代码、改文件、跑测试和审查 diff 都在同一套工作流里。复杂任务的使用体验仍受仓库约定、工具权限和验收信息质量影响。做代码变更时我更看重 diff 和测试证据，做跨渠道任务时更看重触达、状态持续和失败提醒。

「用下来怎么样」可以用两个自己的例子回答。OpenClaw 选一个确实跑过的渠道任务，说清省掉了哪些操作、在哪里要维护。Claude Code 选一个确实做过的代码任务，说清怎么验证改动，以及哪一步仍要人工判断。只看过资料时，可直接说明比较基于公开能力。 [OpenClaw 官方文档](https://docs.openclaw.ai/) · [Claude Code 工作机制](https://code.claude.com/docs/en/how-claude-code-works)
