### 1. Harness 是什么，需要包含哪些内容？

> 从边界看，模型产出动作意图，Harness 把它转成可管控的操作。最小闭环要有模型适配、上下文组装、动作协议、工具执行和终止条件。跑长期任务还需要权限控制、状态持久化、恢复、观测和评测。举例来说，模型可以提出修改文件，是否有权限、补丁作用在哪、失败怎么处理、修改有没有通过测试，都要由运行系统和实际证据决定。

可用 [阿里国际一面第 7 题](<02-阿里国际一面.md#7-harness-是什么包含哪些内容>) 的工具执行示例继续展开。

### 2. 从底层开始是如何设计的？

> 我先定运行契约。模型每步返回一个 `<tool>` 或一个 `<final>`。下面一层是工具注册表和执行器，先校验工具名、参数、路径和权限，再执行并返回结果。上面一层是运行循环，每步组 prompt、调模型、解析结果，工具完成后写回历史和任务证据，再进入下一步。最后把跨轮 session 和单次 run 工件分别存起来，让续跑和排错都能查到需要的数据。

```text
CLI 装配工作区、模型客户端和 session
  → Pico.ask() / AgentLoop
  → ContextManager 组装 prompt → 模型客户端 → 解析文本协议
      ├─ tool  → 校验与执行 → 更新状态、历史、trace 和 checkpoint → 下一步
      ├─ retry → 记录格式问题 → 在重试预算内继续
      └─ final → 收尾并写 report
```

工具步数用尽后，当前实现还可以请求一次仅生成最终答案的收尾。模型返回最终答案代表 run 正常收尾，任务是否完成仍可用测试或 verifier 独立判断。 [主循环](../pico/agent_loop.py) · [执行器](../pico/tool_executor.py) · [评测](../pico/evaluation/evaluator.py)

### 3. 了解 run trace 吗？为什么自己做记录工具，没用现成工具？

> Run trace 是一次运行的事件时间线。我会用它回答某个动作为什么发生、花了多久、失败在哪一层。Pico 是单机 CLI，项目需要离线查看 prompt 裁剪、权限决策和恢复状态，还要用同一批字段聚合 benchmark。按 run 写 JSONL 成本低，断开网络也能直接查到这次调用的时间线。Trace 记录过程，checkpoint 和 session 保存续跑需要的状态。

如果系统扩大到跨进程、模型网关和工具服务，可以把 run 映射为根 span，把模型请求、工具执行映射为子 span，再用 OpenTelemetry 串起延迟和错误。Pico 特有的上下文裁剪原因和恢复状态仍可作为业务属性，导出前对敏感字段做过滤。 [Pico 运行工件](../pico/run_store.py) · [OpenTelemetry Traces](https://opentelemetry.io/docs/concepts/signals/traces/)

### 4. OpenClaw 底层的 4 个工具是什么？

> 按 OpenClaw 文档的核心工具来讲，是 `read` 读文件、`write` 创建或覆盖文件、`edit` 局部编辑、`exec` 执行命令。实际可用工具随配置和权限变化，还会有相关的系统工具。若面试官指的是 Pi 的经典最小工具组合，执行命令的工具名通常写成 `bash`，和 OpenClaw 的 `exec` 对应。

[Pico 之外的参考 · OpenClaw 运行时](https://docs.openclaw.ai/concepts/agent#built-in-tools) · [Pi 官方工具列表](https://github.com/earendil-works/pi/tree/main/packages/coding-agent)

### 5. 如果要把文件记录到数据库，选什么文件数据库？

> 如果指的是 Pico 这样的单机工具，我会选 SQLite 作为本地文件型数据库。先用结构化字段存相对路径、内容哈希、版本、大小、时间和 run ID。小文本需要事务一致性时可以随记录存进库。大日志留在文件系统，数据库存路径和哈希。要按错误码、符号或文本查找，再考虑用 FTS5 索引脱敏后的文本。

例如用 `runs`、`artifacts` 两张表关联运行和文件，给 `run_id` 和路径加索引。外置文件先完整写入，再提交引用，异常时通过校验哈希和清理孤儿文件修复。若变成多机并发写入和集中检索，再评估服务端数据库和对象存储。Pico 当前用本地 JSON、JSONL 和日志文件保存运行数据，SQLite 是这道题的设计选型。 [SQLite FTS5](https://sqlite.org/fts5.html) · [Pico 运行工件](../pico/run_store.py)

### 6. 如何选择 history 放进去？还有什么改进空间？

> 我会先判断一条历史对下一步有没有用，再看它占多少预算。当前 Pico 先在任务状态里放有效约束、未解决错误和验证证据。普通历史从近到远选，优先保留完整的工具事件，放不下就给短表示或文件引用，最后按时间顺序排列。版本已经过期的读结果会提示重读，避免模型把历史内容当成当前文件。

> 改进时我会把近期窗口和旧历史检索结合起来。近期窗口保存动作的连续性，旧历史按任务、文件路径、符号和错误码召回。召回后检查文件版本，按时间和依赖关系排好再送进模型，保留出处。评测用“早期用户约束被忘掉”“报错在长日志尾部”“文件改过后恢复”这三类场景，看遗漏率、任务通过率和 token 开销。
