### 1. 工具有哪些，分别是什么？

> 我按模型的工作顺序来讲。先用 `list_files` 看目录、用 `search` 找符号、用 `read_file` 读证据。改动用 `write_file` 写整份文件，或者用 `patch_file` 定点替换。随后用 `run_shell` 跑测试或检查 diff。需要独立调查时，用 `delegate` 让只读子 Agent 在有限步数内查清一个问题。专用读写工具有明确的参数和权限边界，执行结果也更容易记录和评测。

完整工具表见[阿里云一面第 1 题](<01-阿里云一面.md#1-7-类工具和-3-类运行工件分别是什么>)。 [工具执行](../pico/tool_executor.py)

### 2. 长上下文治理怎么做？只输入 `hi` 时，Prompt 长什么样，占多少 token？

> 上下文治理发生在每次模型调用前。系统保留规则和仓库背景，把任务约束提到记忆区，按预算选历史，并让当前请求完整留在末尾。即使用户只输入 `hi`，模型仍会看到工具说明、协议示例、工作区背景和各段标题。新会话的首次请求先写进 session，所以这个例子里 `hi` 也会出现在历史和任务记忆里。

以空工作区、新会话、默认工具注册和脚本化模型为例，实测首轮是 **3,187 字符**。下面省略了前缀正文和部分记忆行。

```text
[角色规则、工具定义与示例、工作区信息]

Memory:
Active task state:
- Goal: hi
...

Relevant memory:
- none

Transcript:
[user] hi

Current user request:
hi
```

| 段 | 实测字符数 |
| --- | ---: |
| Prefix | 2,984 |
| Memory | 127 |
| Relevant memory | 23 |
| History | 21 |
| Current request（含标题） | 24 |
| 段间空行 | 8 |

如果面试官要一个量级，按英文为主的文本粗略用 4 字符/token 换算，这份样本约 **800 个输入 token**，只是量级估算。精确值要对完整请求用目标模型的 tokenizer 和消息模板计数，或看该后端实际回报的 usage。兼容接口的缓存读写字段也要按服务端口径解释。工作区、工具集合和历史不同，实际值会变。CLI 默认的 **512** 是单步输出上限。 [提示词前缀](../pico/prompt_prefix.py) · [组装逻辑](../pico/context_manager.py) · [后端适配](../pico/providers/clients.py)

### 3. 模型接入做了哪些？自部署模型放在本机还是其他服务器？

> CLI 有四个 provider 选项。Ollama 走 `/api/generate`，OpenAI 兼容走 `/responses`，Anthropic 兼容和 DeepSeek 兼容走 `/messages`。底层是三种客户端实现，DeepSeek 复用 Anthropic-compatible client。主循环通过统一的 `complete()` 接口拿模型输出，工具仍由 Pico 在工作区执行。

| 部署方式 | 适合的场景 | 代价 |
| --- | --- | --- |
| 本机 Ollama | 个人调试、小模型、希望模型输入留在单机内 | 受显存、内存和算力限制，会和开发任务争抢资源 |
| 内网 GPU 推理服务 | 较大模型、团队共用、需要集中管理模型版本 | 多一跳网络和排队，需要维护服务、鉴权和访问日志 |

> 如果我的机器能稳定跑满足任务质量的小模型，我会先本机跑。需要更大的模型或多人共享时，我会把推理放到内网 GPU，Pico 仍留在开发机执行工具。内网服务会收到传去推理的代码片段和工具结果，所以要按实际的数据边界配置访问和留存策略。

早期简历里的“两类后端”按当时版本解释。当前面试口径是 **4 个配置选项、3 种客户端实现**。 [启动与配置](../pico/cli.py) · [模型客户端](../pico/providers/clients.py)

### 4. 当前支持同一个 session 切换模型吗？如何设计？

> 当前 CLI 在启动时选定 model client，交互模式没有 `/model` 命令。可以用不同的 `--provider` 或 `--model`，配合 `--resume <session_id>` 重启并读同一个会话。恢复检查会对照 checkpoint 里的模型名和客户端类型，发现差异会记录。要做原生热切换，我会把 session 里的通用历史和任务证据与当前模型配置分开，只允许在 run 之间切换，并把每个 run 用的模型写进记录。

换模型时按新窗口重组 prompt，保留约束和工具证据，按新后端的消息格式重新编码。若以后接入原生工具调用，适配层需维护调用与结果的关联，并隔离各家特有的 reasoning block、响应 ID 和缓存状态。工作区和工具审批仍由宿主管理。 [CLI 恢复入口](../pico/cli.py) · [运行身份](../pico/checkpoint.py)

### 5. 在同一个 session 切换模型继续做任务，会有什么影响？

> 会话可以延续，但模型对任务的理解要从新 prompt 重建。新模型可能上下文更小、tokenizer 不同，原来的历史放不下。它的工具格式遵循能力和编程能力也可能不同，导致同样的证据走出不同的下一步。缓存通常要重新建立。我会先让新模型拿到任务目标、约束、已做变更、未解决错误和最近验证结果，再按新窗口补普通历史。涉及写入前，我会先核对实际文件和已有测试状态。

切到另一个服务还会改变代码和日志片段的接收方。若要做模型间对照，按 run 记录模型、提示词用量、工具错误和验证结果，才能判断差异来自哪里。

### 6. 三类运行工件是什么？

> 可以按状态、过程、结果来记。`task_state.json` 是单次运行状态，记录尝试次数、工具步骤、结束原因等。`trace.jsonl` 是事件时间线，可以看 prompt 组装、模型调用、工具和 checkpoint。`report.json` 是收尾报告，适合聚合用量、排查失败和做评测对照。比如测试修复失败，我先从 report 看停止原因，再在 trace 找到具体命令和错误，必要时沿工件引用读长日志。

它们按 `.pico/runs/<run_id>/` 归档。跨轮恢复的数据保存在 `.pico/sessions/`。 [运行工件与恢复](../docs/architecture/agent-harness-v1-overview.md)

### 7. Harness 是什么，包含哪些内容？

> Harness 是把模型的决策接进真实执行环境的那层运行系统。模型提出下一步，Harness 负责准备它看到的信息、验证并执行动作、维护状态、决定什么时候停止，以及记录结果。Pico 里主要是运行循环、模型适配、上下文和记忆、工具与权限、会话恢复，以及 trace 和评测。比如模型想跑测试，Harness 会校验命令参数、按策略审批、限时运行，再把退出状态和日志证据交给下一轮。

面试时可以用同一模型、同一任务下的通过率、违规拦截、重复工具调用和恢复成功率解释 Harness 的作用。 [架构总览](../docs/architecture/agent-harness-v1-overview.md)
