# 沙箱概念说明

> **文档生成时间**：2026-08-09
>
> 配套文档：`03-工具的接入与调用设计 (2).md`

## 什么是沙箱

**沙箱（sandbox）就是"把不可信代码/动作关进一个隔离笼子里跑，让它碰不到宿主环境"的机制。** 名字来源于儿童玩的沙坑——孩子在沙坑里怎么折腾都不会伤到自己，沙子也不会跑到外面去。

## 为什么 agent 需要沙箱

agent 的模型能执行 shell、改文件、跑代码。这些动作本身是不可信的——模型可能：

- 跑一条命令时意外删了宿主机的文件
- 执行一个会 `rm -rf /` 的测试
- 恶意/失误地把 `API_KEY` 外传

如果直接在**宿主机**上跑，后果就是整个系统遭殃。沙箱的思路是：**让模型的动作在一个受限环境里发生，即使里面炸了，外面也不受影响**。

## 沙箱要隔离什么

| 隔离维度 | 例子 |
|---|---|
| **文件系统** | 模型只能读写 `/sandbox` 里的文件，看不到 `/home/user/.ssh` |
| **网络** | 禁止访问外网，或只允许白名单域名 |
| **进程** | 不能启动新进程 / 不能 kill 别的进程 |
| **系统调用** | 拒绝 `mount`、`reboot` 等危险调用 |
| **资源** | 限制 CPU、内存、磁盘配额，防止跑死 |

## 实现沙箱的常见手段（从轻到重）

| 手段 | 原理 | 隔离强度 |
|---|---|---|
| **工作目录锁定**（Pico 现在的做法） | `cwd=root` + 路径 `commonpath` 检查 | 弱——只能防路径越界，防不了命令本身 |
| **Docker 容器** | 每次任务起一个容器，`--rm --network=none`，跑完销毁 | 中——文件/网络/进程都隔离 |
| **虚拟机（VM）** | 起一个完整虚拟机跑任务 | 强——硬件级隔离 |
| **seccomp / 系统调用过滤** | 内核层拦截危险 syscall | 强——精细控制 |

## Pico 现在到哪一层了

文档里明确说了：

> 当前没有完整 OS 级沙箱，也没有更细粒度的目录 ACL。它更像一套**运行时治理和工作区约束**。

Pico 现在的边界（对标"工作目录锁定"那一档）：

```
✅ cwd=root（run_shell 只能在仓库根目录跑）
✅ 路径 commonpath 检查（文件工具不能越界）
✅ env allowlist（API key 不传给子进程）
✅ timeout（命令超时会杀掉）
❌ 没有容器/VM（模型还是跑在宿主机的 shell 里）
❌ 没有网络隔离
❌ 没有资源配额
```

也就是说：**Pico 挡的是"路径/环境"这类常见失误，但如果你让模型跑 `rm -rf ~` 这类命令，它真的会删**——因为没有系统级隔离。

## 加了沙箱以后会怎样

如果给 Pico 加 Docker 沙箱：

```python
# 理想中的样子（现在是直接 subprocess.run）
result = docker_run(
    image="python:3.12",
    command=command,
    network="none",        # 禁网
    tmpfs=True,            # 内存盘，任务结束清空
    cwd=f"/sandbox/{run_id}",
)
```

模型跑任何命令都在容器里，删 `rm -rf /` 也只是删容器自己的文件系统，宿主机毫发无损。

## 一句话总结

**沙箱 = 让不可信动作在隔离笼子里执行，笼子内随便折腾，笼子外毫发无损。Pico 目前只有"轻量约束"（目录锁定、env 白名单），不是真正意义的沙箱；真沙箱需要 Docker/VM 这类系统级隔离，这也是文档 PS 里建议有兴趣再扩展的方向。**
