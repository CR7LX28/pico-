# 运行工件与执行证据设计

> **文档生成时间**：2026-08-05

## 背景

主循环负责把一条用户请求推进成一次完整 run，但如果推进过程没有留下任何痕迹，那出了问题就只能靠猜。比如模型在第几轮开始跑偏、工具返回了什么错误、prompt 有没有被裁剪——这些都需要证据。

Pico 的做法是在主循环里内置了三类工件落盘，分别在 run 的不同阶段持续产出。它们不依赖额外的日志脚手架，而是直接从 `ask()` 的 while 循环里写入 `.pico/runs/<run_id>/`。

## 这篇要解决什么问题

一句话：**一次 run 在执行过程中留下了哪些证据，分别回答什么问题，怎么用它们来排错、复盘和评估。**

- task_state 存什么，为什么每轮都写
- trace 记录哪些事件，按什么顺序产出
- report 打包了哪些终局信息
- 三者之间怎么配合，而不是互相替代

## 三类工件概览

Pico 每次 run 会在 `.pico/runs/<run_id>/` 下产出三类工件，分工明确：

| 工件 | 文件 | 写入频率 | 定位 |
|---|---|---|---|
| `task_state.json` | `.pico/runs/<run_id>/task_state.json` | 运行中每轮都写 | 仪表盘——当前跑到哪了 |
| `trace.jsonl` | `.pico/runs/<run_id>/trace.jsonl` | 运行中每发生一个事件就追加 | 监控录像——过程里发生了什么 |
| `report.json` | `.pico/runs/<run_id>/report.json` | 运行结束时写一次 | 结案报告——最后结果和关键指标 |

---

## task_state.json

### 记录什么

本轮 run 的**运行时状态快照**，总共 12 个字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `run_id` | `string` | 运行 ID，格式 `run_YYYYMMDD-HHMMSS-xxxxxx` |
| `task_id` | `string` | 任务 ID，格式 `task_YYYYMMDD-HHMMSS-xxxxxx` |
| `user_request` | `string` | 用户的原始请求文本 |
| `status` | `string` | 当前状态：`running` / `completed` / `stopped` / `failed` |
| `stop_reason` | `string` | 停止原因：`final_answer_returned` / `step_limit_reached` / `retry_limit_reached` 等 |
| `tool_steps` | `int` | 工具调用总次数（只统计真正进入执行阶段的） |
| `attempts` | `int` | 模型被调用的总轮数 |
| `last_tool` | `string` | 最后一次调用的工具名（空串表示尚未调用） |
| `final_answer` | `string` | 最终回答文本（运行中为空串） |
| `checkpoint_id` | `string` | 检查点 ID（空串表示无） |
| `resume_status` | `string` | 恢复状态，共 5 种取值，见下表 |

### resume_status 的五种取值

定义在 `pico/checkpoint.py` 中：

| 常量 | 值 | 含义 | 什么时候出现 |
|---|---|---|---|
| `CHECKPOINT_NONE_STATUS` | `"no-checkpoint"` | 没有任何检查点 | 新 run，第一次运行 |
| `CHECKPOINT_FULL_VALID_STATUS` | `"full-valid"` | 检查点全部有效 | 上次检查点后的文件没变、身份没变 |
| `CHECKPOINT_PARTIAL_STALE_STATUS` | `"partial-stale"` | 检查点部分过期 | 检查点记录的部分文件 freshness 变了 |
| `CHECKPOINT_WORKSPACE_MISMATCH_STATUS` | `"workspace-mismatch"` | 运行身份不匹配 | 换机器 / 换用户 / 换模型 / 配置变了 |
| `CHECKPOINT_SCHEMA_MISMATCH_STATUS` | `"schema-mismatch"` | 检查点格式不兼容 | 旧版本检查点遇到新代码（schema_version 对不上） |

**判断逻辑**（`evaluate_resume_state()`）：无检查点 → `no-checkpoint`；有检查点则依次判断——schema 对不上 → `schema-mismatch`；文件 freshness 变了 → `partial-stale`（优先级最高）；身份字段不匹配 → `workspace-mismatch`；都没问题 → `full-valid`。

**主循环如何响应**：`partial-stale` 和 `workspace-mismatch` 会在调模型前触发检查点预处理（建新检查点 + 写 trace）；`no-checkpoint` / `full-valid` 直接跳过；`schema-mismatch` 目前无专门分支，按"不可用"处理。

### 示例（运行中 vs 完成后）

**运行中**（刚启动，第一轮模型调用前）：
```json
{
  "attempts": 1,
  "checkpoint_id": "",
  "final_answer": "",
  "last_tool": "",
  "resume_status": "no-checkpoint",
  "run_id": "run_20260709-005128-a2b63a",
  "status": "running",
  "stop_reason": "",
  "task_id": "task_20260709-005128-8ce984",
  "tool_steps": 0,
  "user_request": "你好"
}
```

**完成后**（模型返回 final answer）：
```json
{
  "attempts": 4,
  "checkpoint_id": "ckpt_8c581fc8",
  "final_answer": "当前 agent 配置使用的模型是 **deepseek-v4-pro**...",
  "last_tool": "read_file",
  "resume_status": "no-checkpoint",
  "run_id": "run_20260804-162215-49a951",
  "status": "completed",
  "stop_reason": "final_answer_returned",
  "task_id": "task_20260804-162215-efa854",
  "tool_steps": 3,
  "user_request": "当前agent使用的是什么模型"
}
```

### 为什么每轮都要写

主循环中每调用一次模型，都会立即写 `task_state.json`。这样：
- 外部工具或脚本可以随时读取来观察进度
- 运行中途崩溃时，至少能看到最后跑到哪一步
- 排查问题时不需要等整轮跑完

## trace.jsonl

### 记录什么

按时间顺序记录**本轮 run 的逐事件时间线**。每行一个 JSON 对象，通过追加写入（append-only）。

### 事件类型及携带信息

| 事件 | 触发时机 | 携带的关键信息 |
|---|---|---|
| `run_started` | run 初始化完成，主循环开始前 | `task_id`、`user_request`（裁剪到 300 字符） |
| `prompt_built` | 每轮重组 prompt 之后 | `prompt_metadata`（包含各 section 字符数、hash、缓存键等）、组合耗时 |
| `model_requested` | 即将调用模型时 | `attempts`、`tool_steps`、`prompt_cache_key` |
| `model_parsed` | 模型返回并被 `parse()` 解析之后 | `kind`（`tool` / `final` / `retry`）、模型返回的 completion metadata、调用耗时 |
| `tool_executed` | 工具执行完毕之后 | `name`、`args`、`result`（裁剪到 500 字符）、执行耗时、工具返回的 metadata |
| `checkpoint_created` | 创建检查点时 | `checkpoint_id`、`trigger`（触发原因：`tool_executed` / `freshness_mismatch` / `workspace_mismatch` / `context_reduction` / `run_finished` 等） |
| `runtime_identity_mismatch` | 工作区身份不匹配时 | `fields`（不匹配的字段列表） |
| `run_finished` | run 终止时（无论成功还是达到上限） | `status`、`stop_reason`、`final_answer`、本轮总耗时 |

### 每条事件的通用结构

```json
{
  "event": "tool_executed",
  "created_at": "2026-08-04T16:22:20",
  "name": "read_file",
  "args": {"path": "pyproject.toml"},
  "result": "[toolu_bdrk_01...] 读取到 45 行内容...",
  "duration_ms": 12
}
```

### 用途

- **排错**：工具返回了什么、模型第几轮开始跑偏、哪次 prompt 重建了
- **回放**：按时间线完整重演一轮 run 的全过程
- **评估**：统计工具调用分布、模型调用耗时、检查点触发频率

## report.json

### 记录什么

本轮 run 的**终局摘要**，只在运行结束时写一次。它把 `task_state` 的最终快照和 `prompt_metadata` 全部打包进一份文件。

### 字段结构

| 字段 | 类型 | 说明 |
|---|---|---|
| `run_id` | `string` | 运行 ID |
| `task_id` | `string` | 任务 ID |
| `status` | `string` | 最终状态 |
| `stop_reason` | `string` | 停止原因 |
| `final_answer` | `string` | 最终回答 |
| `tool_steps` | `int` | 工具调用总次数 |
| `attempts` | `int` | 模型调用总轮数 |
| `checkpoint_id` | `string` | 检查点 ID |
| `resume_status` | `string` | 恢复状态 |
| `task_state` | `object` | **完整的 `task_state` 最终快照**（嵌套了整个 task_state 的所有字段） |
| `prompt_metadata` | `object` | **最后一轮 prompt 的组合详情**（见下方子结构） |
| `durable_promotions` | `array` | 成功提升为持久记忆的条目 |
| `durable_rejections` | `array` | 被拒绝的持久记忆条目 |
| `durable_superseded` | `array` | 被替换的持久记忆条目 |
| `redacted_env` | `object` | 敏感环境变量摘要（`secret_env_count` + `secret_env_names`） |

### `prompt_metadata` 子结构

| 子字段 | 说明 |
|---|---|
| `prompt_chars` / `prompt_budget_chars` / `prompt_over_budget` | 最终 prompt 总字符数、预算上限、是否超预算 |
| `prefix_chars` / `prefix_hash` / `prefix_changed` | 前缀字符数、哈希、本轮是否变化 |
| `workspace_chars` / `workspace_fingerprint` / `workspace_changed` | 工作区描述字符数、指纹、是否变化 |
| `workspace_docs` / `recent_commits` | 项目文档数、最近提交数 |
| `memory_chars` / `history_chars` / `request_chars` | 记忆、历史、请求各自的字符数 |
| `tool_count` / `tool_signature` | 可用工具数及其签名哈希 |
| `prompt_cache_key` / `prompt_cache_supported` | 缓存键及后端是否支持缓存 |
| `resume_status` | 恢复状态 |
| `stale_summary_invalidations` / `stale_paths` | 过期摘要的失效数和路径列表 |
| `runtime_identity_mismatch_fields` | 身份不匹配的字段 |
| `secret_env_count` / `secret_env_names` | 敏感环境变量数及名称 |
| `sections` | 各 section（prefix / memory / relevant_memory / history / current_request）的**预算字符数**与**实际渲染字符数** |
| `section_order` | section 的排列顺序 |
| `section_budgets` | 各 section 的预算分配 |
| `reduction_order` | 超预算时的压缩顺序 |
| `budget_reductions` | 实际触发的预算压缩记录 |
| `current_request` | 当前请求的详细字符统计 |
| `history` | 历史部分的详细统计（去重读文件数等） |
| `relevant_memory` | 相关记忆的详细统计（选中数、来源等） |

### 示例（简化）

```json
{
  "run_id": "run_20260804-162215-49a951",
  "status": "completed",
  "stop_reason": "final_answer_returned",
  "tool_steps": 3,
  "attempts": 4,
  "task_state": { /* task_state.json 的完整快照 */ },
  "prompt_metadata": {
    "prompt_chars": 6170,
    "prompt_budget_chars": 12000,
    "prompt_over_budget": false,
    "sections": {
      "prefix":     { "budget_chars": 3600, "rendered_chars": 3600 },
      "memory":     { "budget_chars": 1600, "rendered_chars": 264  },
      "history":    { "budget_chars": 5200, "rendered_chars": 2238 },
      "current_request": { "budget_chars": null, "rendered_chars": 37 }
    },
    "tool_count": 7,
    "prefix_changed": false,
    "workspace_changed": false
  },
  "durable_promotions": [],
  "redacted_env": { "secret_env_count": 1, "secret_env_names": ["PICO_DEEPSEEK_API_KEY"] }
}
```

### 用途

- **快速复盘**：一眼看到最终状态、用了多少步、停的原因
- **Benchmark**：对比多轮 run 的 `tool_steps`、`attempts`、各 section 消费量
- **归因分析**：`prompt_metadata` 里的 `budget_reductions` 能告诉你 prompt 是否被裁剪过、哪个 section 被压缩了

## 三者关系总结

```
一次 run 的时间线：

[run_started]
    │
    ├── 每轮循环写 task_state.json（实时快照）
    ├── 每轮循环追加 trace.jsonl（逐事件）
    │
    ▼
[run_finished] ──► 写 report.json（终局摘要）
```

| 维度 | `task_state.json` | `trace.jsonl` | `report.json` |
|---|---|---|---|
| 数据量 | 最小（~300B-2KB） | 中（逐事件累积） | 最大（包含前两者 + metadata，~4-6KB） |
| 写入频率 | 高频（每轮） | 高频（每个事件） | 低频（仅结束时） |
| 回答什么问题 | 现在跑到哪了 | 过程里每一步发生了什么 | 这一轮整体花了多少资源、结果怎样 |
| 适合谁看 | 外部监控脚本 / 调试时快速定位 | 深度排错 / 回放 / 评测 | 复盘 / Benchmark / 报告生成 |
