# 会话状态与会话记忆

> **文档生成时间**：2026-08-05

## 背景

runtime 在推进一次执行时，需要同时维护四类信息：

| 层 | 本质 | 谁消费 | 落盘 |
|---|---|---|---|
| **History** | 对话流水 | 模型（进 prompt） | `session.json` (数组追加) |
| **Trace** | 事件日志 | 人（排错/评测） | `trace.jsonl` (JSONL 追加) |
| **Memory** | 结构化笔记 | 模型（进 prompt） | `session.json` + `.pico/memory/` |
| **TaskState** | 运行状态机 | 人+程序（监控/恢复） | `task_state.json` (高频覆盖写) |

这四类信息在 Pico 里各自独立维护，各自的职责、生命周期、落盘文件都不同。同一份工具执行结果，四种视角同时落盘，各司其职。

## 这篇要解决什么问题

- session history 里到底记什么，什么时候写，什么时候读
- Trace 里记了什么事件，什么时候追加，给人排错用
- Memory 的分层结构：Working Memory 和 Durable Memory 各自存什么、怎么更新
- TaskState 的每个字段各管什么，在主循环里怎么变
- 四者怎么各司其职，而不是互相替代

---

## session history

### 是什么

`self.session["history"]` 是个**列表**，存着本轮会话从开始到现在的所有对话记录。通过 `self.record()` 追加，落盘为 `session.json`。

### 里面记什么

每条记录是一个字典，按角色分三类：

| 角色 | 什么时候写 | 记录内容 |
|---|---|---|
| `"user"` | 用户每发一条消息 | `{"role": "user", "content": "...", "created_at": "..."}` |
| `"tool"` | 每次工具执行完毕 | `{"role": "tool", "name": "read_file", "args": {...}, "content": "结果...", "created_at": "..."}` |
| `"assistant"` | 模型给出最终答案 / 遇到 retry 提示 | `{"role": "assistant", "content": "...", "created_at": "..."}` |

### 在主循环里的写入时机

在 `agent_loop.py` 里可以串起来：

```
用户发消息  → record({"role": "user", ...})        # 第18行
模型调工具  → 执行完 record({"role": "tool", ...})   # 第145行
模型输出坏  → record({"role": "assistant", ...})     # 第179行（retry 提示）
模型给答案  → record({"role": "assistant", ...})     # 第184行（最终答案）
```

### 怎么被消费

每轮循环重建 prompt 时，`history_text()` 把 history 列表渲染成文本塞进 prompt，模型每轮都能看到"对话上下文"。近期条目保留更多细节，早期条目会被裁剪或去重（比如重复读同一文件只保留一次）。

### 生命周期

**跨 run 持续累积**。一次会话可以包含多轮 run，history 不会因为新 run 开始而清空，除非显式调用 `reset()`。

## Trace

### 是什么

Trace 是**每次 run 的逐事件时间线**，以 **JSONL 格式逐条追加写入** `.pico/runs/<run_id>/trace.jsonl`。它面向的是**人和程序**（不进 prompt），用于排错、回放和评测。

### 记录的事件类型

| 事件 | 触发时机 | 携带信息 |
|---|---|---|
| `run_started` | run 初始化完成 | `task_id`、`user_request` |
| `prompt_built` | 每轮重组 prompt 后 | 各 section 字符数、hash 等，含耗时 |
| `model_requested` | 即将调模型 | `attempts`、`tool_steps`、`prompt_cache_key` |
| `model_parsed` | 模型输出被 `parse()` 解析后 | `kind`（tool/final/retry），completion metadata，耗时 |
| `tool_executed` | 工具执行完毕 | `name`、`args`、`result`（裁剪到 500 字符）、耗时 |
| `checkpoint_created` | 创建检查点 | `checkpoint_id`、触发原因 |
| `runtime_identity_mismatch` | 工作区身份不匹配 | 不匹配的字段列表 |
| `run_finished` | run 终止 | `status`、`stop_reason`、`final_answer`、总耗时 |

### 写入方式

JSONL 流式追加写入（append-only），保证即使中途异常也不会丢失整份 trace。每条事件写完立刻落盘。

### 与 session history 的关键区别

- **session history 进 prompt**，trace 不进——trace 是纯审计/复盘用的
- **session history 跨 run 累积**，trace 每次 run 独立
- **session history 进 prompt 时会裁剪**，trace 完整保留所有事件

## Memory

### 是什么

Memory 是 Pico 中设计最复杂的一层，分两类：

- **Working Memory**（`self.session["memory"]`）：随会话存活，落盘在 `session.json`
- **Durable Memory**（`.pico/memory/MEMORY.md` + `.pico/memory/topics/*.md`）：跨会话持久化，单独文件存储

核心目标：**减少重复读取，保留跨轮有用的局部事实，跨会话延续长期知识。**

### Working Memory — 四层结构

| 层 | 字段 | 作用 | 上限 |
|---|---|---|---|
| 任务摘要 | `working.task_summary` | 当前任务的短描述，作为跨轮锚点 | 300 字符 |
| 最近文件 | `working.recent_files` | 最近接触过的文件路径，去重保留 | 最多 8 个 |
| 文件摘要 | `file_summaries` | 每个已读文件的短摘要，带 freshness（SHA256）校验 | 每条 500 字符 |
| 会话笔记 | `episodic_notes` | 跨轮笔记，支持轻量召回 | 最多 12 条，每条 500 字符 |

### 核心机制

- **工具结果回写**（`update_memory_after_tool()`）：`read_file` → 生成摘要记入 memory；`write_file`/`patch_file` → 让旧摘要失效
- **Freshness 校验**：每条文件摘要都带文件内容 SHA256 哈希；渲染时重新计算，不匹配则丢弃
- **轻量召回**（`retrieval_candidates()`）：不用 embedding，只用 tag 精确命中 + 关键词重叠 + 时间新旧排序，选出 top 3 笔记注入 prompt

### Durable Memory — 跨会话长期事实

**与 Working Memory 的关键区别**：不塞在 session JSON 里，而是单独落盘到文件系统，面向**跨会话仍然成立的长期事实**。

**四个默认主题**：

| 主题 | 含义 |
|---|---|
| `project-conventions` | 项目约定 |
| `key-decisions` | 关键设计决策 |
| `dependency-facts` | 依赖和环境事实 |
| `user-preferences` | 用户偏好 |

**写入机制**：不是自动写入，需要通过 **promotion gate**——模型输出中匹配特定模式（如 `Decision: ...`、`Preference: ...`）且通过安全检查（不能是敏感信息、不能是临时任务状态）的条目，才会被提升为耐久记忆。

## TaskState

### 是什么

`TaskState` 是一个 Python `@dataclass`，用它兜住**单次 run** 的所有计数与状态。一次请求 = 一个 TaskState 实例，落盘为 `task_state.json`。

### 11 个字段

| 字段 | 类型 | 默认值 | 谁改 | 说明 |
|---|---|---|---|---|
| `run_id` | `str` | 必填 | 创建时固定 | 运行 ID，格式 `run_YYYYMMDD-HHMMSS-xxxxxx` |
| `task_id` | `str` | 必填 | 创建时固定 | 任务 ID，格式 `task_YYYYMMDD-HHMMSS-xxxxxx` |
| `user_request` | `str` | 必填 | 创建时固定 | 用户的原始请求文本 |
| `status` | `str` | `"running"` | `stop()` / `finish_success()` | 当前状态 |
| `tool_steps` | `int` | `0` | `record_tool()` 每次 +1 | 工具执行次数（只统计进入执行阶段的） |
| `attempts` | `int` | `0` | `record_attempt()` 每次 +1 | 模型被调用的总轮数 |
| `last_tool` | `str` | `""` | `record_tool()` 更新 | 最后一次调用的工具名 |
| `stop_reason` | `str` | `""` | `stop()` / `finish_success()` | 停止原因 |
| `final_answer` | `str` | `""` | `finish_success()` / `stop()` | 最终回答文本 |
| `checkpoint_id` | `str` | `""` | 主循环中外部赋值 | 检查点 ID（空串表示无） |
| `resume_status` | `str` | `""` | 创建时外部赋值 | 恢复状态：`no-checkpoint` / `full-valid` / `partial-stale` |

### 状态常量

**status 的四种取值：**

| 常量 | 值 | 含义 |
|---|---|---|
| `STATUS_RUNNING` | `"running"` | 正在运行 |
| `STATUS_COMPLETED` | `"completed"` | 正常完成（模型返回了 final answer） |
| `STATUS_STOPPED` | `"stopped"` | 被停止（达到步数上限或重试上限） |
| `STATUS_FAILED` | `"failed"` | 异常失败（模型错误等） |

**stop_reason 的全部取值：**

| 常量 | 值 | 含义 |
|---|---|---|
| `STOP_REASON_FINAL_ANSWER_RETURNED` | `"final_answer_returned"` | 模型返回了最终答案 |
| `STOP_REASON_STEP_LIMIT_REACHED` | `"step_limit_reached"` | 达到工具步数上限 |
| `STOP_REASON_RETRY_LIMIT_REACHED` | `"retry_limit_reached"` | 达到重试次数上限 |
| `STOP_REASON_MODEL_ERROR` | `"model_error"` | 模型调用出错 |
| `STOP_REASON_TOOL_TIMEOUT` | `"tool_timeout"` | 工具执行超时 |
| `STOP_REASON_APPROVAL_DENIED` | `"approval_denied"` | 审批被拒绝 |
| `STOP_REASON_DELEGATE_FAILED` | `"delegate_failed"` | 委派失败 |
| `STOP_REASON_PERSISTENCE_ERROR` | `"persistence_error"` | 持久化错误 |
| `STOP_REASON_RESUME_LOAD_ERROR` | `"resume_load_error"` | 恢复加载错误 |

### status 和 stop_reason 为什么分开

同一个 `stopped` 状态，原因可能是步数耗尽，也可能是重试过多。分开存，归因时就不会把"正常用完了配额"和"模型一直在输出垃圾"混成一团。

### 在主循环里的生命周期

`agent_loop.py` 中每一步都在操作 TaskState：

```
第20行  create(...)                         → 创建，status = "running"
第46行  task_state.record_attempt()         → attempts +1（每轮循环）
第46行  run_store.write_task_state(...)     → 写出 task_state.json（实时快照）
第141行 task_state.record_tool(name)        → tool_steps +1，更新 last_tool
第185行 task_state.finish_success(final)    → status → "completed"，stop_reason → "final_answer_returned"
第212行 task_state.stop_retry_limit(...)    → status → "stopped"，stop_reason → "retry_limit_reached"
第215行 task_state.stop_step_limit(...)     → status → "stopped"，stop_reason → "step_limit_reached"
```

### 两个工厂方法

| 方法 | 用途 | 调用位置 |
|---|---|---|
| `create(task_id, user_request, run_id?)` | 新建 TaskState，自动生成 run_id | `agent_loop.py` 第20行 |
| `from_dict(data)` | 从 `task_state.json` 反序列化还原 | 恢复 / 加载场景 |

## 四者关系总结

同一份工具执行结果，从四种视角同时落盘，解决四个不同的问题：

| 维度 | History | Trace | Memory | TaskState |
|---|---|---|---|---|
| 本质 | 对话流水（列表） | 事件日志（JSONL） | 结构化笔记（多层） | 运行状态机（dataclass） |
| 记录什么 | 谁说了什么、工具返回了什么 | 每一步事件（prompt_built、tool_executed...） | 文件摘要、近期文件、笔记、长期事实 | 跑到第几轮、调了多少工具、怎么停的 |
| 谁消费 | **模型**（每轮进 prompt） | **人**（排错/评测） | **模型**（进 prompt） | **人+程序**（监控/恢复） |
| 生命周期 | 跨 run 累积（会话级） | 每次 run 独立 | 跨 run（working）/ 跨会话（durable） | 每次 run 独立 |
| 落盘文件 | `session.json` | `trace.jsonl` | `session.json` + `.pico/memory/` | `task_state.json` |
| 写入方式 | 每轮追加 | JSONL 流式追加 | 工具执行后更新 | 高频覆盖写 |
| 裁剪策略 | 进 prompt 时智能压缩 | 不裁剪（完整保留） | 数量上限（8 files / 12 notes） | 不裁剪（固定字段） |

### 在主循环中的并行写入

以模型调工具后为例（`agent_loop.py` tool 分支）：

1. **`record()`** → 写 session history：工具结果完整进对话历史，给下轮模型看
2. **`write_task_state()`** → 写 task_state.json：更新计数器（tool_steps / last_tool），给监控看
3. **`emit_trace()`** → 写 trace.jsonl：裁剪后摘要 + 耗时 + 元数据，给排错看
4. **`update_memory_after_tool()`** → 更新 memory：提取高价值信息（文件摘要、近期文件列表），给下轮模型看

### 一句话区分

| | 告诉谁 | 告诉什么 |
|---|---|---|
| **History** | 模型 | "你之前说过什么" |
| **Trace** | 人 | "过程里到底发生了什么" |
| **Memory** | 模型 | "你该记住什么" |
| **TaskState** | 人+程序 | "现在跑到哪了、怎么停的" |
