## 四、四个核心问题（面试会问）

### 问题 1：一条工具调用从模型输出到真正执行，一共经过多少道检查？每道检查拦什么？

按 `ToolExecutor.execute()` 代码顺序：

```python
# 第 1 关：allowed_tools 白名单检查（可选）
if agent.allowed_tools is not None and name not in agent.allowed_tools:
    return "tool_not_allowed"

# 第 2 关：工具是否存在
tool = agent.tools.get(name)
if tool is None:
    return "unknown_tool"

# 第 3 关：参数校验 validate_tool()
agent.validate_tool(name, args)  # 抛出异常即拒绝

# 第 4 关：重复调用拦截
if agent.repeated_tool_call(name, args):
    return "repeated_identical_call"

# 第 5 关：高风险工具审批
if tool["risky"] and not agent.approve(name, args):
    return "approval_denied"

# 第 6-7 关（隐式）：执行异常兜底 + workspace diff
# 通过 try/except 包裹执行体，失败后依然对比快照
```

**关键认知**：这 7 关全部是**先拦后跑**——前 5 关在执行前就能拒绝，后 2 关在执行中/后兜底。

### 问题 2：patch_file 为什么必须 `count == 1`？这个约束牺牲了什么、换来了什么？

```python
if name == "patch_file":
    count = text.count(old_text)
    if count != 1:
        raise ValueError(f"old_text must occur exactly once, found {count}")
```

**牺牲了**：不能批量替换、不能模糊匹配、模型必须精确复制原文片段。

**换来了**：
- 失败原因完全确定：要么 0 次（文本不存在），要么多次（歧义）
- 不会出现"我以为只改了一处，实际上改了 5 处"的静默错误
- 对于 agent 场景，**可解释的错误比静默的错误更安全**

#### 为什么必须"正好命中一次"——三种出现次数场景对比

`old_text` 在文件里出现的次数有三种情况：

| 出现次数 | 模型的意图 | 不限制会怎样 |
|---|---|---|
| `0` 次 | 模型记错了，文件里根本没有这段 | 替换无效，文件没改但模型以为改了，下轮决策基于错误信息 |
| `1` 次 | 命中目标，正常替换 | 正确替换 |
| `2+` 次 | 模型给的 `old_text` 太短或太泛，没指定到唯一位置 | 替换错位置，可能改坏文件，且事后极难追溯 |

最危险的是"次数 > 1"的情况：模型可以"成功"返回，但实际改的是错误的位置，这种 bug 后面很难追——文件改了、内容变了，但改的不是你想改的地方。

所以 Pico 选择**严格拒绝不是"正好一次"的情况**，宁可不改也不能改错地方。模型会收到 `old_text must occur exactly once, found N` 的错误，被迫重新读文件、给更长的 `old_text` 锁定到唯一位置再试。

这种保守设计的代价是：模型可能要重试几次才能改成功。换来的是：**每次成功的 patch 都是确定的、可解释的，不会产生模糊的副作用。**

### 问题 3：resolved path + commonpath 为什么能挡住符号链接逃逸？

`runtime.py:771-779`：

```python
def path(self, raw_path):
    path = Path(raw_path)
    path = path if path.is_absolute() else self.root / path
    resolved = path.resolve()  # 解析所有符号链接
    if os.path.commonpath([str(self.root), str(resolved)]) != str(self.root):
        raise ValueError(f"path escapes workspace: {raw_path}")
    return resolved
```

三步原理：
1. 相对路径先拼到 root 下
2. `resolve()` 把符号链接展开成真实路径——即使模型构造 `/repo/innocent_link` 指向 `/etc/passwd`，resolve 后变成 `/etc/passwd`
3. `commonpath` 比较——`/repo` 和 `/etc/passwd` 的公共前缀是 `/`，不等于 `/repo`，拒绝

所以不只能挡住 `../` 字符串逃逸，还能挡住符号链接间接逃逸。

### 问题 4：`ToolExecutor.execute()` 的返回值为什么是 `ToolExecutionResult`（content + metadata）而不是纯字符串？

因为 agent_loop 需要的不只是"工具返回了什么文本"，还需要知道：
- `tool_status`（ok / rejected / error / partial_success）
- `affected_paths`（执行后改了哪些文件）
- `workspace_changed`（有没有产生副作用）
- `tool_error_code`（拒绝的具体原因）

这些 metadata 写入 trace 和 report 后，才能回答"这 3 步工具调用中，第 2 步为什么被拒绝了"。纯字符串只能看到"发生了什么"，metadata 能看到**"为什么发生"和"影响范围"**。

## 五、自测问题清单（含答案）

### Q1：`tool_context.py` 只给工具暴露了 5 个东西，目的是什么？

```python
@dataclass
class ToolContext:
    root: Path
    path_resolver: Callable[[str], Path]
    shell_env_provider: Callable[[], dict]
    depth: int
    max_depth: int
    spawn_delegate: Callable[[dict], str]
```

**目的**：工具函数不能随意访问 runtime。只能通过 `ToolContext` 提供的狭窄接口操作。`path_resolver` 自带路径逃逸检查，工具调用时不需要（也不应该）自己实现路径安全逻辑。这是一种**能力限制 = 安全保障**的设计模式——接口越窄，越难被误用。

---

### Q2：3 种 approval_policy 在代码里怎么表现？优先级是什么？

`runtime.py:631-642`：

```python
def approve(self, name, args):
    if self.read_only:       return False            # 全局只读模式，最高优先级
    if self.approval_policy == "auto":   return True
    if self.approval_policy == "never":  return False
    # "ask" 模式：弹交互等待用户输入
    answer = input(f"approve {name} ...? [y/N] ")
    return answer.strip().lower() in {"y", "yes"}
```

优先级：**`read_only` > policy 值**。不论 policy 是 `auto` / `never` / `ask`，只要 `read_only=True` 一律拒。

### Q3：`run_shell` 的 4 层约束分别是什么？哪层最容易被忽视？

| 约束 | 代码位置 | 作用 |
|------|---------|------|
| `cwd=agent.root` | `tools.py` 子进程调用 | 工作目录锁定仓库根 |
| `timeout` 1~120s | `tools.py` `validate_tool()` | 防止命令阻塞整个 run |
| `env=agent.shell_env()` | `tools.py` 子进程调用 | **环境变量走 allowlist** |
| 输出裁剪 | `clip()` | 防止长输出撑满 prompt |

**最容易被忽视的是 allowlist env**（`runtime.py:29`）：

```python
DEFAULT_SHELL_ENV_ALLOWLIST = ("HOME", "LANG", "LC_ALL", "LC_CTYPE",
    "LOGNAME", "PATH", "PWD", "SHELL", "TERM", "TMPDIR", "TMP", "TEMP", "USER")
```

这意味着 `API_KEY`、`TOKEN`、`SECRET` 这类敏感环境变量不会随 `subprocess.run()` 传给子进程——即使模型让你跑 `echo $API_KEY`，也拿不到值。这不是完整沙箱，但挡掉了一大类信息泄露风险。

### Q4：`repeated_tool_call()` 为什么只看最近 2 条事件？如果是间歇性重复（比如 A→B→A）能拦住吗？

```python
def repeated_tool_call(self, name, args):
    tool_events = [item for item in self.session["history"] if item["role"] == "tool"]
    if len(tool_events) < 2:
        return False
    recent = tool_events[-2:]   # 只看最近两次工具事件
    return all(item["name"] == name and item["args"] == args for item in recent)
```

**A→B→A 拦不住**。需要最近两次都是同一个调用才拦。设计意图是：如果模型做了别的动作后又回来，中间那步可能提供了新信息，所以放行。只拦"什么新信息都没有、纯重复发送"的最蠢循环，避免误杀。

### Q5：执行中的 workspace snapshot diff 有什么价值？

`tool_executor.py:112-117`：

```python
before_snapshot = agent.capture_workspace_snapshot() if tool["risky"] else {}
# ... 执行工具 ...
after_snapshot = agent.capture_workspace_snapshot() if tool["risky"] else before_snapshot
affected_paths, diff_summary = agent.diff_workspace_snapshots(before_snapshot, after_snapshot)
```

价值：
- 工具只说自己"成功了"，但**到底改了哪几个文件、是不是改到了不该改的地方**，只有 diff 能回答
- 只对 `risky=True` 的工具做 snapshot——低风险工具不做，省性能
- `diff_summary`（`created:...` / `modified:...` / `deleted:...`）写进 trace，复盘时快速定位副作用
- 执行异常时也会 diff——即使报错了，可能已有部分文件被修改，`metadata` 里的 `partial_success` 状态标记了这种情况

## 六、学完要能讲顺的链路

不看文档，能顺着讲出：

> Pico 的工具层是一条受控执行链。工具先在 `tools.py` 用 `BASE_TOOL_SPECS` 显式注册，每个工具带 schema / risky / description 三元组。模型发起调用后，不直接执行，而是统一进入 `ToolExecutor.execute()`：先查 allowed_tools → 工具是否存在 → 参数校验（patch_file 要求精确出现 1 次） → 重复调用拦截 → 审批（read_only 最高优先级） → 执行前快照 → 真正执行 → 执行后 diff → 返回 `ToolExecutionResult`（content + metadata）。路径通过 `commonpath` 对比钉死在工作区（包括符号链接逃逸），shell 走 allowlist env。这样模型的每个动作都落在明确、可校验、可拒绝、可审计的边界内。

讲不顺的节点，就是没吃透的地方。03 的核心不是"接了哪些工具"，而是"工具调用怎么被约束"。
