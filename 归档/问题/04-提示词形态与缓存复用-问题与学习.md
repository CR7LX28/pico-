## 四、四个核心问题（面试会问）

### 问题 1：PromptPrefix 为什么带 5 个字段，而不是只存一段文本？

`prompt_prefix.py:11-19`：

```python
@dataclass
class PromptPrefix:
    text: str                    # 真正写进 prompt 的文本
    hash: str                    # 前缀文本的 SHA-256
    workspace_fingerprint: str   # 工作区摘要的签名
    tool_signature: str          # 工具表面的签名
    built_at: str                # 生成时间
```

如果只存 `text`，runtime 就无法回答"前缀为什么变了"——是工作区变了？还是工具表面变了？分开存三个签名后：
- `workspace_fingerprint` 变 → 仓库状态变了（分支/git status/文档）
- `tool_signature` 变 → 工具集合变了（比如 delegate 因为深度耗尽被移除）
- `hash` 变 → 前缀文本整体变了（上面两个或规则文本本身变了）

**核心价值**：失效归因能做细，而不是只知道"变了"。

---

### 问题 2：refresh_prefix() 每轮都跑，为什么不会拖慢系统？

`runtime.py:213-234`：

```python
def refresh_prefix(self, force=False):
    refreshed_workspace = WorkspaceContext.build(self.root)       # 每轮重建 workspace
    refreshed_workspace_fingerprint = refreshed_workspace.fingerprint()
    workspace_changed = force or refreshed_workspace_fingerprint != previous_workspace_fingerprint
    if workspace_changed:
        self.workspace = refreshed_workspace

    prefix_state = self.build_prefix() if workspace_changed or force or previous_hash is None else self.prefix_state
```

关键：**每轮重建的是 workspace 对象 + 算一次 fingerprint（哈希），不是重建 prefix 文本**。`build_prefix()` 只在 fingerprint 变了时才调用。fingerprint 计算只是把 7 个字段打包做 SHA-256，开销远小于重新拼系统规则 + 工具说明 + 工作区摘要那整段文本。

所以"每轮判断"是廉价的，"重建前缀"是偶尔发生的。

---

### 问题 3：哪些变化会让前缀失效？哪些不会？为什么这样划分？

**会让前缀失效**（来自 `workspace.py:138-151` 的 fingerprint 字段）：

| 变化 | 影响 |
|------|------|
| 分支变化 | 模型对仓库状态的理解变了 |
| git status 变化 | 未提交改动变了 |
| 最近提交变化 | 仓库历史变了 |
| README/AGENTS 等文档变化 | 项目说明变了 |
| 工具表面变化 | `tool_signature` 变（如 delegate 因深度耗尽消失） |

**不会让前缀失效**：
- history 变化
- memory 变化
- 当前用户请求变化

**为什么这样划分**：前缀装的是"agent 的工作手册"（我是谁、工具怎么用、仓库什么状态），这些是相对稳定的事实。history/memory/请求是动态段，本来就该每轮重建，不该混进前缀失效逻辑。混进来的后果是：cache 永远命中不了，因为 history 每轮都在变。

---

### 问题 4：cache 链路从发出到收回，完整经过哪些环节？

完整链路（跨 4 个文件）：

```
1. prompt_prefix.py:90     hash = SHA256(prefix.text)
                              ↓
2. runtime.py:325          prompt_cache_key = prefix_state.hash
                              ↓
3. agent_loop.py:134       prompt_cache_key = prompt_metadata.get("prompt_cache_key")
                           （只在 supports_prompt_cache=True 时才发）
                              ↓
4. clients.py:276-279      payload["prompt_cache_key"] = prompt_cache_key
                           （进入 HTTP 请求体）
                              ↓
5. 后端返回 usage 结构
                              ↓
6. clients.py:209-223      _extract_usage_cache_details() 抽出 cached_tokens / cache_hit
                              ↓
7. clients.py:326-330      写入 self.last_completion_metadata
                              ↓
8. agent_loop.py:127-133   prompt_metadata.update(completion_metadata)
                           （并回本轮 metadata）
                              ↓
9. trace.jsonl + report.json  最终落盘，可观测
```

**关键设计**：cache key 用的是 `prefix_hash`（稳定段签名），**不是整段 prompt 的哈希**。如果用整段哈希，history 每轮变一次，cache 就永远 miss。用 prefix hash 才能保证"稳定部分被复用，动态部分按轮重建"。

## 五、自测问题清单（含答案）

### Q1：为什么 `supports_prompt_cache` 要按 base_url 判断，而不是统一设为 True？

`clients.py:235`：

```python
self.supports_prompt_cache = any(host in self.base_url for host in ("openai.com", "right.codes"))
```

因为 cache 是 provider 特定语义。如果后端不支持 `prompt_cache_key` 参数，硬传过去要么被忽略（浪费），要么报错（更糟）。**"看起来统一、其实没意义"的伪参数比不传更危险**——你会以为 cache 在工作，其实没有。保守判断确保只有真支持的后端才走这条链路。

---

### Q2：Ollama 和 Anthropic-compatible 后端为什么 `supports_prompt_cache = False`？

`clients.py:40`（Ollama）和 `clients.py:369`（Anthropic-compatible）都是硬编码 `False`。

- Ollama 本地接口没有 prompt cache 语义
- Anthropic-compatible 虽然理论上有 cache_control，但 Pico 当前没有实现这条适配

所以 runtime 在 `agent_loop.py:133` 判断 `supports_prompt_cache` 为 False 时，`prompt_cache_key` 保持 `None`，根本不发这个参数。

---

### Q3：prefix 里除了系统规则和工具说明，还有一段 `workspace.text()`。这段是什么？

`prompt_prefix.py:84`：`{workspace.text()}` 被拼进前缀末尾。这是 `WorkspaceContext` 生成的工作区摘要——包含当前目录、仓库根、分支、git status、最近提交、项目文档片段。它是前缀里**最容易变的部分**，所以 `workspace_fingerprint` 单独拎出来做失效判断。

---

### Q4：checkpoint_text 也会被拼进 prefix，这会不会破坏 cache？

`context_manager.py:114-118`：

```python
checkpoint_text = str(self.agent.render_checkpoint_text() or "").strip()
if checkpoint_text:
    section_texts["prefix"] = section_texts["prefix"] + "\n\n" + checkpoint_text
```

**会**。checkpoint_text 拼进 prefix 后，`prefix.hash` 会变，cache key 就变了。但这是设计权衡——checkpoint 信息（当前目标、卡点、下一步）对模型决策很重要，宁可让 cache 失效也要带上。checkpoint 只在恢复场景或工具执行后才会变，不是每轮都变，所以影响可控。

---

### Q5：`_extract_usage_cache_details()` 为什么要同时兼容 `input_tokens` 和 `prompt_tokens` 两种字段名？

`clients.py:213-214`：

```python
input_tokens = usage.get("input_tokens", usage.get("prompt_tokens"))
```

因为不同 OpenAI-compatible 后端返回的 usage 结构字段名不统一。`/responses` 接口用 `input_tokens`，老的 `/chat/completions` 用 `prompt_tokens`。`_extract_usage_cache_details()` 做了一层归一化，让 runtime 不用关心 provider 细节。同理 `input_tokens_details` 和 `prompt_tokens_details` 也都兼容。

## 六、学完要能讲顺的链路

不看文档，能顺着讲出：

> Pico 把 prompt 里的稳定部分单独拎出来管理。系统规则、工具说明、工作区摘要先组成一份 `PromptPrefix`，带 text / hash / workspace_fingerprint / tool_signature / built_at 五个字段。每轮请求前，`refresh_prefix()` 会先重建 workspace 并算 fingerprint，和旧值比较——没变就复用原 prefix，变了才重建。然后在 `OpenAICompatibleModelClient` 上（按 base_url 判断支持），把 prefix_hash 作为 `prompt_cache_key` 发给后端。响应回来后，`_extract_usage_cache_details()` 从 usage 里抽出 `cached_tokens` 和 `cache_hit`，并回 prompt_metadata，最终进入 trace 和 report。这样稳定部分被认真复用，动态部分（history/memory/请求）还是按轮重建。

讲不顺的节点，就是没吃透的地方。04 的核心不是"prompt 怎么拼"，而是"稳定段怎么被管理和复用"。
