## 二、按文档顺序的学习要点（每节盯住什么）

### 1. ask() 开头先做什么（初始化 7 步）
盯住 `agent_loop.py:18-39`。要点：**一次请求 = 一次独立 run**，run_id 和 task_id 绑死。注意初始化顺序——先写 memory 的 task_summary → 再记 history → 再建 TaskState → 再开 run 目录 → 再发第一条 trace。想清楚为什么是这个顺序（TaskState 必须在 run 目录之前建好，trace 又必须依赖 run 目录）。

### 2. 主循环四阶段（最重要）
`agent_loop.py:51-184`，这是整篇核心。把循环体拆成四个阶段对应到代码：
- **感知** = `agent._build_prompt_and_metadata()`（第 56 行）
- **决策** = `model_client.complete()` + `parse()`（第 121、134 行）
- **行动** = `execute_tool()`（第 151 行，仅 tool 分支）
- **记录** = `record()` + `write_task_state()` + `emit_trace()`（散落各处）

**必须想透的对比**：`attempts`（模型被调几轮）vs `tool_steps`（真正执行的工具数）。文档说的"attempts 高但 tool_steps 低 = 一直在 retry"——对照 `max_attempts = max(max_steps*3, max_steps+4)`（第 43 行）理解为什么重试上限比步数上限宽松。

### 3. 为什么 prompt 每轮重建
看 `runtime.py:308-338`。重点不是"重建"本身，而是**重建时顺手带出的 metadata**（prefix_hash、workspace_fingerprint、tool_signature、prompt_cache_key）。想清楚：metadata 不是装饰，它是 trace 和 report 能解释"这轮发生了什么"的基础。

### 4. parse() 三分支（面试高频）
`runtime.py:644-694`。三种返回：`tool` / `final` / `retry`。盯住两个细节：
- 支持两种工具格式：`<tool>{json}</tool>` 和 XML 风格 `<tool name="...">`（第 665、681 行）
- `<final>` 和 `<tool>` 同时出现时，按**出现先后**判断（第 665 行的 `raw.find` 比较）——这个细节容易被追问

### 5. 工具结果怎么回到主循环（闭环）
`agent_loop.py:151-184`。工具执行后做了 5 件事：record 进 history → write_task_state → emit_trace(tool_executed) → **create_checkpoint** → continue 回循环顶。**关键认知**：工具没有脱离主循环，它是一条"出去再回来"的路，不是岔路。注意第 174 行——每次工具执行后都会建 checkpoint，trigger 是 `tool_executed`。

### 6. TaskState 为什么是中心状态
`task_state.py` 全文很短，但 `status` 和 `stop_reason` 分开存是核心设计（第 74-80 行注释明说了）。背下 4 种 status（running/completed/stopped/failed）和对应 stop_reason。想清楚：为什么不混成一个字段？因为 benchmark 和失败归因需要区分"现在什么状态"和"为什么停"。

### 7. 循环什么时候停
`agent_loop.py:218-247`。三类停止：
- final answer → `finish_success`（第 193 行）
- step limit → `stop_step_limit`（第 223 行）
- retry limit → `stop_retry_limit`（第 220 行）

注意循环退出后的判定逻辑（第 218 行）：`attempts >= max_attempts and tool_steps < max_steps` 才算 retry limit，否则算 step limit。

### 8. 三类工件落盘时机
在 `agent_loop.py` 里数 `write_task_state` / `emit_trace` / `write_report` 各出现几次、在什么时机：
- `task_state.json`：每轮都写（高频）
- `trace.jsonl`：每个事件追加（最高频）
- `report.json`：只在结束时写一次（第 215、246 行）

## 三、四个必须想透的核心问题（面试会问）

### 问题 1：attempts 和 tool_steps 有什么区别？attempts=10 但 tool_steps=2 说明什么？

**区别：**
- `attempts`：统计模型被调了几轮，每次 `attempts += 1` 都发生在进入循环体之后（`agent_loop.py:52`）
- `tool_steps`：只统计真正进入工具执行（`kind == "tool"`）的次数（`agent_loop.py:146`）。解析失败、`retry`、直接 `final` 都不计。

**attempts=10, tool_steps=2 说明：** 模型被调了 10 轮，但只有 2 次发出了有效的工具调用，其余 8 次大概率是输出格式不合法（触发了 `retry` 分支）。常见原因：模型持续输出 malformed JSON、空响应、或格式不符合 `parse()` 预期。这个对比值直接暴露了模型输出质量的问题，而不是工具执行的效率问题。

**为什么重试上限更宽松：**

```43:43:agent_loop.py
max_attempts = max(agent.max_steps * 3, agent.max_steps + 4)
```

因为格式修正通常比真正的工具执行轻量——如果模型只是输出格式有问题，给几次重试机会就能纠正；但如果真正执行了 max_steps 次工具操作，任务本身可能已经无效了。

---

### 问题 2：工具执行完以后，结果怎么影响下一轮 prompt？

闭环链路（`agent_loop.py:151-184`）：

**第一步**：工具结果通过 `agent.record()` 写入 `session["history"]`：

```153:161:agent_loop.py
agent.record(
    {
        "role": "tool",
        "name": name,
        "args": args,
        "content": result,
        "created_at": now(),
    }
)
```

**第二步**：循环回到顶部后，`_build_prompt_and_metadata()`（`agent_loop.py:56`）调用 `context_manager.build()`，而 `ContextManager` 会读取 `self.agent.session["history"]` 和 `self.agent.memory_text()` 来组装 prompt。`history_text()`（`runtime.py:239-263`）会把最近 6 条历史以 900 字符截断、更早历史以 180-220 字符截断后拼接进去。

**第三步**：模型在新一轮 prompt 里看到完整的对话历史（包含上一轮的工具调用和结果），从而基于最新信息做出下一步决策。

**同时**，`update_memory_after_tool()`（`runtime.py:388-420`）也会从工具结果里提取轻量摘要写进 `LayeredMemory`，比如 `read_file` 会记文件摘要、`write_file`/`patch_file` 会让旧摘要失效。

### 问题 3：status 和 stop_reason 为什么要分开存？

直接看 `task_state.py` 的设计：

```27:39:task_state.py
@dataclass
class TaskState:
    run_id: str
    task_id: str
    user_request: str
    status: str = STATUS_RUNNING       # "现在什么状态"
    tool_steps: int = 0
    attempts: int = 0
    last_tool: str = ""
    stop_reason: str = ""              # "为什么停"
    final_answer: str = ""
    checkpoint_id: str = ""
    resume_status: str = ""
```

两个字段各回答不同的问题：
- `status`：`running` → `completed` / `stopped` / `failed`（当前状态的标签）
- `stop_reason`：`final_answer_returned` / `step_limit_reached` / `retry_limit_reached` / `model_error` 等（停机原因）

**如果只有一个字段会丢失什么信息？**

举例：status 只有 `failed`，但你不知道是模型自身异常（`model_error`）还是被审批拒绝（`approval_denied`）还是重试耗尽（`retry_limit_reached`）。做 benchmark 聚合时，`completed` + `step_limit_reached`、`stopped` + `step_limit_reached`、`failed` + `retry_limit_reached` 是完全不同的失败模式，归因和优化方向也完全不同。分开存让失败归因可以做多维交叉分析（如"有哪些 completed 但其实是靠 step limit 强制结束的"），而不是把所有非正常终止混成一个模糊的"失败"。

### 问题 4：prompt 每轮重建，但 cache 还能命中，为什么？

关键在于 **prefix 部分（系统规则 + 工具 schema + 工作区基线）在大多数轮次里是不变的**，变的主要是 history 和 memory。

**cache 机制**（`agent_loop.py:114-119`）：

```114:119:agent_loop.py
prompt_cache_key = None
prompt_cache_retention = None
if getattr(agent.model_client, "supports_prompt_cache", False):
    prompt_cache_key = prompt_metadata.get("prompt_cache_key")
    prompt_cache_retention = "in_memory"
```

`prompt_cache_key` 来自 `prefix_state.hash`（`runtime.py:325`），即 prefix（系统指令 + 工具定义 + 工作区描述）的哈希。只要工作区、工具列表没变，prefix 的 hash 就不变，cache key 就不变。

**refersh_prefix() 的失效判断**（`runtime.py:213-234`）：

```222:226:runtime.py
workspace_changed = force or refreshed_workspace_fingerprint != previous_workspace_fingerprint
if workspace_changed:
    self.workspace = refreshed_workspace

prefix_state = self.build_prefix() if workspace_changed or force or previous_hash is None else self.prefix_state
```

只有当 workspace fingerprint 变化（文件增删、git 状态改变）时才重建 prefix。所以 **cache key 只在"前缀真正变化"时才会变**，大多数轮次 cache 仍然命中。

**注意**：只有 OpenAI-compatible 后端（`OpenAICompatibleModelClient`）真正支持 prompt cache，Ollama 和 Anthropic-compatible 路径不支持（`supports_prompt_cache` 为 `False`，`prompt_cache_key` 保持 `None` 不发出）。

## 四、自测问题清单（含答案）

### Q1：run_started 这条 trace 在什么时机发？为什么 task_summary 要在 record history 之前写？

**时机**：`run_started` trace 在 7 步初始化完成后、while 循环开始之前发出（`agent_loop.py:32-39`）。此时 TaskState 已创建、run 目录已建好、resume_status 已标记。

**为什么 task_summary 在 record history 之前写**（对比第 19 行和第 21 行）：

```18:21:agent_loop.py
agent.memory.set_task_summary(user_message)                          # [1]
agent.record({"role": "user", "content": user_message, ...})          # [2]
```

`set_task_summary()` 写入的是 `LayeredMemory` 的 `task` 字段，而 `record()` 写入的是 `session["history"]`。两者的用途不同：
- `task_summary`：在 `_build_prompt_and_metadata` 中被 `ContextManager.build()` 引用，作为 memory section 的一部分——它描述的是**"本轮任务目标是什么"**，在整个 run 过程中保持不变
- `session history`：是对话记录，后续还会追加 assistant / tool 消息

先写 task_summary 再写 history 没有严格的依赖关系，但逻辑上"先定目标再记日志"更清晰。

---

### Q2：模型返回里同时有 `<tool>` 和 `<final>`，runtime 怎么判？依据是什么？

看 `runtime.py:644-694` 的 `parse()`，核心逻辑：

```python
# 情况 1：<tool> 先出现（且 <final> 不存在 或 <tool> 出现更早）
if "<tool>" in raw and ("<final>" not in raw or raw.find("<tool>") < raw.find("<final>")):
    # ... 解析为 tool 调用
    return "tool", payload

# 情况 2：XML 风格 <tool name="..."> 先出现
if "<tool" in raw and ("<final>" not in raw or raw.find("<tool") < raw.find("<final>")):
    # ... 解析为 tool 调用
    return "tool", payload

# 情况 3：有 <final> 标签
if "<final>" in raw:
    return "final", final

# 情况 4：没有任何标签但有文本内容
if raw.strip():
    return "final", raw.strip()
```

**依据**：按标签出现的先后顺序判断。`raw.find("<tool>") < raw.find("<final>")`——谁在文本里先出现谁说了算。如果 `<tool>` 出现在 `<final>` 之前（且 tool 解析成功），runtime 就认为模型的意思是"我还要做事"；只有当 `<tool>` 解析失败或不存在时，才轮到 `<final>`。

### Q3：checkpoint 在一轮里最多建几次？分别在什么 trigger 下建？

checkpoint 的创建散布在 `agent_loop.py` 的 `run()` 里，一共 **5 种 trigger**：

| 触发位置 | trigger | 条件 |
|---------|---------|------|
| `agent_loop.py:66` | `freshness_mismatch` | prompt_metadata 的 resume_status = `partial-stale`（恢复时文件已变化） |
| `agent_loop.py:84` | `workspace_mismatch` | resume_status = `workspace-mismatch`（工作区指纹 / 工具签名 / 模型等不匹配） |
| `agent_loop.py:95` | `context_reduction` | 本轮 prompt 触发了预算裁剪（`budget_reductions` 不为空） |
| `agent_loop.py:174` | `tool_executed` | **每轮工具执行后**都会建（最常见） |
| `agent_loop.py:195` | `run_finished` | 拿到 final answer 时 |
| `agent_loop.py:227` | `step_limit_reached` 或 `retry_limit_reached` 或 `run_stopped` | 非正常退出时 |

**单轮最多可能建几个？** 理论上一次循环里如果同时触发了 freshness_mismatch + budget_reductions + tool_executed，那就是 3 个 checkpoint。但 freshness_mismatch 和 workspace_mismatch 互斥（`if...elif`），所以同一轮最多不会同时触发这两个。

### Q4：delegate 子 agent 走不走同一个主循环？

**走**。`runtime.py:588-608` 的 `spawn_delegate()`：

```588:608:runtime.py
def spawn_delegate(self, args):
    task = str(args.get("task", ""))
    child = Pico(
        model_client=self.model_client,
        workspace=self.workspace,
        session_store=self.session_store,
        run_store=self.run_store,
        approval_policy="never",       # 子 agent 不弹审批
        max_steps=int(args.get("max_steps", 3)),  # 步数更少
        max_new_tokens=self.max_new_tokens,
        depth=self.depth + 1,
        max_depth=self.max_depth,
        read_only=True,                # 只读
        ...
    )
    child.session["memory"]["task"] = task
    child.session["memory"]["notes"] = [clip(self.history_text(), 300)]
    return "delegate_result:\n" + child.ask(task)  # 调用同一套 ask() → AgentLoop.run()
```

子 agent 创建了一个新的 `Pico` 实例，然后调用 `child.ask(task)` → `AgentLoop(self).run(task)`，走的是**完全相同的主循环**。区别在于运行时约束：
- `read_only=True`：所有写操作会被 `approve()` 拒绝（`runtime.py:632-633`）
- `approval_policy="never"`：连已读工具也会静默拒绝，不弹交互
- `max_depth` 限制嵌套层数，防止无限委派
- 子 agent 的结果最终作为普通文本追加 `"delegate_result:\n"` 前缀后返回

**本质**：delegate 只是在一个更受限的边界里，递归复用同一套主循环。

### Q5：max_attempts 公式为什么是 `max(max_steps*3, max_steps+4)` 而不是直接等于 max_steps？

```43:43:agent_loop.py
max_attempts = max(agent.max_steps * 3, agent.max_steps + 4)
```

两个退出条件是 `tool_steps < agent.max_steps and attempts < max_attempts`，它们保护的目标不同：

- `tool_steps < max_steps`：防止工具执行次数失控。默认 `max_steps=6`，即最多执行 6 次真正的工具操作
- `attempts < max_attempts`：防止模型因格式问题无限重试。默认 `max_attempts = max(18, 10) = 18`

**如果 `max_attempts == max_steps`（比如都等于 6），会发生什么？**

假设模型在尝试 read_file 时输出了 malformed JSON，这会触发 `retry`，但 `attempts` 也 +1。如果连续 6 次输出格式都有问题，attempts 就用完了——但 tool_steps 还是 0，实际上一件工具操作都没执行到。这个任务就死在了"格式纠错"阶段，连工具都没机会碰。

**所以公式的设计意图是**：给格式修正留出比"真正干活"多 3 倍的冗余空间。格式问题通常比工具执行轻量（只是让模型重新输出），多给几次机会是合理的。而 `max_steps+4` 作为下限保证即使 `max_steps` 很小（如 1-2），也至少有 5-6 次尝试机会。
