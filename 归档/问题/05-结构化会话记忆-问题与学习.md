## 四、四个核心问题（面试会问）

### 问题 1：记忆四层各解决什么问题？为什么是这四层，不是一个大摘要？

| 层 | 字段 | 解决什么 | 上限 |
|----|------|---------|------|
| 任务摘要 | `working.task_summary` | history 被裁后模型还有锚点知道在干什么 | 300 字符 |
| 最近文件 | `working.recent_files` | 下一轮不用从头猜碰过哪些文件 | 8 个（`WORKING_FILE_LIMIT`） |
| 文件摘要 | `file_summaries` | 不用重读文件就知道刚读到了什么 | 6 个（`FILE_SUMMARY_LIMIT`） |
| 跨轮笔记 | `episodic_notes` | 跨轮还值得带走的短结论 | 12 条（`EPISODIC_NOTE_LIMIT`） |

**不做大摘要的原因**：大摘要不可解释——你不知道它为什么留了这条、丢了那条。拆成四层后，每层的输入来源明确（task_summary 来自用户请求、recent_files 来自工具调用、file_summaries 来自 read_file 结果、episodic_notes 来自工具结果提纯），失效逻辑也各自独立。

---

### 问题 2：file_summaries 的 freshness 机制怎么工作？有哪两道失效防线？

`features/memory.py:470-481`——写入摘要时带 freshness（文件内容 SHA-256）：

```python
state["file_summaries"][path] = {
    "summary": summary,
    "created_at": now(),
    "freshness": file_freshness(path, workspace_root),  # 文件内容哈希
}
```

**第一道防线——主动失效**（`runtime.py:419-420`）：

```python
elif name in {"write_file", "patch_file"}:
    self.memory.invalidate_file_summary(canonical_path)  # 直接 pop
```

write_file / patch_file 执行后，对应路径的旧摘要立即被删除。

**第二道防线——渲染时校验**（`features/memory.py:574-576`）：

```python
current_freshness = file_freshness(path, workspace_root)
if summary.get("summary", "") and summary.get("freshness") == current_freshness:
    summaries.append(f"- {path}: {summary['summary']}")
```

`render_memory_text()` 渲染时重算文件哈希，对不上就不显示。这挡住了"文件被外部修改（比如手动编辑或 git checkout）但 runtime 不知道"的情况。

**两道防线的关系**：第一道处理 runtime 自己改了文件的情况（即时），第二道处理外部改动（惰性，渲染时才发现）。

### 问题 3：retrieval_candidates() 的召回逻辑为什么不用 embedding？4 维排序各自的作用？

`features/memory.py:519-547`：

```python
exact_tag_match = int(bool(query_tokens & note_tags))   # 第 1 维：tag 精确命中
keyword_overlap = len(query_tokens & note_tokens)        # 第 2 维：关键词重叠数
recency = _parse_timestamp(note.get("created_at"))       # 第 3 维：时间新旧
note_index = int(note.get("note_index", 0))              # 第 4 维：插入顺序
ranked.append(((exact_tag_match, keyword_overlap, recency, note_index), note))
ranked.sort(key=lambda item: item[0], reverse=True)
```

**不用 embedding 的原因**：
- embedding 召回不可解释——你不知道这条笔记为什么被选中
- 笔记数量很少（上限 12 条 + durable 的几十条），不需要语义近似来筛
- 规则透明意味着可以调试：召回结果不对时，能直接查是哪一维出了问题

**4 维排序的优先级**：
1. tag 精确命中（0 或 1）——最高优先，说明笔记直接关联当前请求涉及的文件/主题
2. 关键词重叠数——tag 没命中时，看文本本身有没有共同词
3. 时间新旧——前面都一样时，新的优先
4. 插入顺序——最后兜底，保证排序确定性

### 问题 4：记忆是怎么和工具执行链绑定的？为什么只绑 read_file / write_file / patch_file？

`runtime.py:388-420` 的 `update_memory_after_tool()`：

```python
if name in {"read_file", "write_file", "patch_file"}:
    self.memory.remember_file(canonical_path)      # 三类都记路径
if name == "read_file":
    summary = memorylib.summarize_read_result(result)
    self.memory.set_file_summary(canonical_path, summary)      # 生成摘要
    self.memory.append_note(summary, tags=(canonical_path,), source=canonical_path)  # 追加笔记
elif name in {"write_file", "patch_file"}:
    self.memory.invalidate_file_summary(canonical_path)        # 失效旧摘要
```

**为什么只绑这三类**：
- `read_file` 是信息获取——读到的内容值得留摘要，减少下一轮重复读取
- `write_file` / `patch_file` 是状态变更——变更后旧摘要必然过期，必须失效
- `run_shell` / `search` / `list_files` / `delegate` 的结果不进 file_summaries，因为它们不是文件级事实

**绑定的位置**：`update_memory_after_tool()` 在 `tool_executor.py:130` 被调用——工具执行完之后、下一轮 prompt 组装之前。完整结果已经进了 history，这里只做轻量提纯。

## 五、自测问题清单（含答案）

### Q1：`render_memory_text()` 为什么不展开 episodic_notes 的正文，只显示数量？

`features/memory.py:583`：`f"- episodic_notes: {len(state['episodic_notes'])}"`

因为笔记正文通过另一条路进 prompt——`relevant_memory` section。`ContextManager.build()` 会调 `retrieval_candidates(user_message, limit=3)` 按当前请求召回 top 3 笔记。如果仪表盘里也展开全部笔记，就会和 relevant_memory 重复，白白占预算。**仪表盘只告诉模型"有 N 条笔记"，召回才告诉它"哪 3 条和当前请求相关"**。

---

### Q2：`summarize_read_result()` 怎么把文件内容压成摘要？为什么取前 3 行？

`features/memory.py:505-516`：

```python
def summarize_read_result(result, limit=180):
    lines = [line.strip() for line in str(result).splitlines() if line.strip()]
    if not lines:
        return "(empty)"
    if lines[0].startswith("# "):
        lines = lines[1:]       # 跳过 markdown 标题行
    summary = " | ".join(lines[:3])  # 前 3 行非空行
    return clip(summary, limit)      # 裁到 180 字符
```

取前 3 行是因为：文件开头通常是 import / 函数签名 / 类定义 / 模块文档——这些已经足够提醒模型"这个文件大概是干什么的"。完整内容已经在 history 里，memory 只需要留一个"锚"，不需要复制全文。

---

### Q3：`invalidate_stale_file_summaries()` 和 `invalidate_file_summary()` 有什么区别？什么时候各被调用？

| 函数 | 触发方式 | 调用时机 |
|------|---------|---------|
| `invalidate_file_summary(path)` | 主动——指定路径删除 | `write_file` / `patch_file` 执行后（`runtime.py:420`） |
| `invalidate_stale_file_summaries()` | 批量——遍历所有摘要，逐个比 freshness | 会话恢复时（`runtime.py:157-160`，`invalidate_stale_memory()`） |

前者是"我知道这个文件刚被改了，立即清掉"。后者是"恢复会话时，我不知道哪些文件在外部被改过，全部重新校验一遍"。

---

### Q4：记忆实验里的 `memory_irrelevant` 对照组是什么？为什么需要它？

文档提到 `metrics.py` 里有 memory on / off / irrelevant 三组对照：
- `memory_on`：正常记忆
- `memory_off`：关闭记忆（`feature_flags["memory"] = False`）
- `memory_irrelevant`：开启记忆，但塞的是和当前任务无关的笔记

**为什么需要 irrelevant 组**：如果只做 on/off，`memory_on` 比 `memory_off` 好，你无法区分收益来自"结构化相关记忆"还是"单纯多塞了点上下文"。`memory_irrelevant` 组排除了这个混淆——如果 irrelevant 也能带来同样收益，说明记忆的价值只是"prompt 更长了"，而不是"记忆真的相关"。

当前结果：`memory_irrelevant` 没有带来同样收益，证明收益确实来自结构化和相关性。

### Q5：`canonicalize_path()` 做了什么？为什么记忆里要用 canonical path？

`features/memory.py:265-272`：

```python
def canonicalize_path(raw_path, workspace_root=None):
    resolved = resolve_workspace_path(raw_path, workspace_root)
    # ... 解析符号链接、转为相对 root 的 posix 路径
    return resolved.relative_to(root).as_posix()
```

它把 `./src/foo.py`、`/abs/repo/src/foo.py`、`src/../src/foo.py` 统一成 `src/foo.py`。

**为什么重要**：如果模型上一轮用 `./src/foo.py` 读文件，下一轮用 `src/foo.py` 再读，不做 canonicalize 的话 memory 会当成两个不同文件，recent_files 里出现重复，file_summaries 也对不上。canonicalize 保证了"同一个文件不管怎么写路径，在记忆里都是同一个 key"。

## 六、学完要能讲顺的链路

不看文档，能顺着讲出：

> Pico 的记忆层不是知识库，是轻量工作记忆，分四层：task_summary（任务锚点）、recent_files（最近碰过的文件）、file_summaries（文件短摘要）、episodic_notes（跨轮笔记）。记忆和工具链绑定——read_file 会生成摘要并追加笔记，write_file / patch_file 会主动失效旧摘要。file_summaries 带 freshness（文件内容 SHA-256），渲染时重算哈希对比，外部改动也能被发现。召回不用 embedding，用 4 维排序（tag 命中 > 关键词重叠 > 新旧 > 插入顺序），结果可解释。下一轮 prompt 里 memory section 是仪表盘（只显示数量），relevant_memory section 才按当前请求召回 top 3 笔记。实验上有 on / off / irrelevant 三组对照，证明收益来自结构化相关性而不是单纯多塞上下文。

讲不顺的节点，就是没吃透的地方。05 的核心不是"记住了什么"，而是"记忆怎么保持可信"。
